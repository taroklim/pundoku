# @pundoku/web

PWA-клиент Pundoku: React 19 + Vite + i18next (en/uk/ru). Экраны: Today (PD-12), Play (PD-11), Year (PD-25).

```sh
pnpm dev:web            # vite :5173, запросы /api/* проксируются на localhost:3000 (apps/api)
pnpm --filter @pundoku/web build && pnpm --filter @pundoku/web exec vite preview   # прокси работает и в preview
pnpm --filter @pundoku/web test                                                    # vitest
```

В проде web отдаётся nginx-контейнером (`apps/web/Dockerfile`, `apps/web/nginx/`), тот же nginx проксирует `/api/*` на api —
один origin, CORS не нужен, `VITE_API_BASE_URL` пуст (см. `DEPLOY.md` в корне репо).

`VITE_API_BASE_URL` (build-time) — base URL api. Пусто — тот же origin (dev-прокси Vite). В проде — публичный
адрес api без завершающего `/`; `WEB_ORIGIN` api должен содержать origin web. Service worker не кэширует `/api/*`
(`navigateFallbackDenylist`).

## Экран Today (PD-12)

Игровая механика (ввод, заметки, undo, таймер, M1/M3, лог ходов) — общая с Play: `play/gameStore.ts`
(`GameStore`), общие UI-части — `play/controls.tsx`, карточка результата — `play/ResultCard.tsx`.
`PlayStore` берёт сетку из Worker-генератора, `DayStore` (`today/dayStore.ts`) — из API либо фолбэка.
Сторы живут выше вкладок: смена вкладки партию не сбрасывает (таймер на паузе, пока вкладка не на экране).

### Какая сетка дня играется (`today/dayResolver.ts`, чистый модуль, тесты `dayResolver.test.ts`)

Дата — **локальная** дата устройства (`YYYY-MM-DD`). Сервер принимает до «завтра» по UTC включительно.

1. Сетка дня — ответ `GET /api/daily/:date` (`mission`, `difficulty`, `winRate?`, `source: sudoku.com | generator`).
   Решение клиент вычисляет сам: `solve(mission)` движка (сервер `solution` не отдаёт). `mission` без решения
   (противоречивая сетка) трактуется как «ответа не было». **Единственность решения клиент не проверяет**:
   `solve` берёт первое найденное решение. Осознанно: сетки Sudoku.com и генератора единственны (проверено
   2026-09-29 на 45 последних днях реального API Sudoku.com — 45/45 `countSolutions === 1`, найденное решение
   совпало с `solution` из ответа), а неединственная сетка не должна ломать день «нет ответа».
2. **Нет ответа** (офлайн, 5xx/404/429, таймаут 8 с, невалидный JSON) — клиентский фолбэк, и **только**
   `dailyPuzzle(date, difficulty)` движка (в Web Worker: для тяжёлых сложностей это секунды). `difficulty`:
   из ответа API, если он был **и `source: generator`**; иначе последняя известная за сессию (тоже только у
   `generator`); иначе `DAILY_FALLBACK_DIFFICULTY` (`medium`). Метка сложности Sudoku.com (`hard`/`expert`…) —
   чужая шкала, не сложность генератора: она не запоминается и в фолбэк не идёт, иначе после смены суток в
   офлайне одна дата давала бы разные сетки в зависимости от истории сессии (`dailyPuzzle(date,'hard')` против
   `dailyPuzzle(date,'medium')` на сервере). Для подписи метка Sudoku.com при этом показывается как есть.
   Seed вручную не собирается — сетка обязана совпасть с серверным фолбэком.
   Константа заведена в web отдельно: движок её не экспортирует, значение должно совпадать с `DAILY_FALLBACK_DIFFICULTY`
   сервера (`apps/api`, по умолчанию `medium`).
3. **Медленный сервер**: API отвечает дольше 2,5 с — начинаем играть фолбэком; поздний ответ сверяется по п. 4.
   Офлайн (`navigator.onLine === false`) фолбэк без ожидания.
4. **Сверка при возврате в сеть** (событие `online`, возврат вкладки/приложения на экран): день перезапрашивается
   (`fetch` с `cache: "no-cache"` — фолбэк-сетка отдаётся с `max-age=60`) и сверяется по `mission`/`source`:

   | Ситуация | Что делаем |
   |---|---|
   | Ответа нет | остаёмся как есть (помечаем «офлайн») |
   | Та же `mission` | обновляем `source`/`winRate`, проверка решения — на сервере (`POST verify`) |
   | Другая `mission`, ходов нет | молча берём актуальную сетку |
   | Другая `mission`, ходы есть | доигрываем свою; проверка **локальная** (verify на сервер не шлём), win rate не показываем |

   «Ходы» — любая запись в логе (цифра, стирание, заметка, undo). Сетка `sudoku.com` неизменна — её не перезапрашиваем.
   Смена суток: если день не начат либо решён, при возврате на экран грузится новый день; начатый вчерашний доигрывается.
   **Таймера на полночь нет — осознанно**: смена дня замечается только по событию `online` / `visibilitychange`
   (или следующей загрузке экрана). iOS при возврате из фона (в т. ч. PWA) присылает `visibilitychange`, а держать
   таймер в свёрнутой PWA бессмысленно (iOS его замораживает); открытый после полуночи экран продолжает показывать
   вчерашний день до первого такого события.
5. **Решение** проверяется на сервере (`POST /api/daily/:date/verify`) только для сетки, совпавшей с серверной;
   ответ `false` скрывает «N % solved today». Нет ответа — день всё равно решён (проверено локально).
6. Подпись «Wed 29 Sep · Medium · 4:12». Если сложность источника движку неизвестна — без сложности.
   Ярлык источника (минимальный, без бренд-ассетов): «Puzzle from Sudoku.com» / «Puzzle from Pundoku's generator» /
   «Made on this device» (клиентский фолбэк).
7. Прогресс дня сохраняется в репозитории (см. ниже) и переживает смену вкладки; решённый день финален
   (без сети и анимации сразу карточка).

### Карточка дня (после решения)

`ResultCard`: тепловая карта `heatmap(moveLog)` (в макете — «Your path»; время движка переводится в ранги, чтобы
одна долгая пауза не сжала карту в два оттенка), «Technique reached» (`summary`), время, clean/число правок,
«N % solved today» — только после решения и если API отдал `winRate` для этой сетки. Кнопки (PD-129): **«Watch your solve»
— главная** (залитая `--ink`), **Share — вторичная** (тонированная `--ink-tint`, как «New game»); без цельного лога делиться
нечем — Share **не показывается вовсе** (не серая), а вместо Watch стоит тихая строка. Цели ≥ 44 pt, в том числе в уплотнённой
карточке на низком экране (320×568). Подробнее — раздел про Таймлапс ниже.

### Grid ∞ — постоянная сетка (`today/permanent.ts`, `repository.ts`)

Концепция — `reports/sudoku-pwa-research/07-concept-draft.md`: у сетки с самого начала скрытое решение; игрок
управляет позицией (клетка последнего хода решённой сетки дня), цифра берётся из скрытого решения.

**Решения developer'а** (концепция их не фиксирует — ждут подтверждения PM/владельца):

- Скрытое решение: `generate({ difficulty: "easy", seed: "grid-inf/<installSeed>/<index>" }).solution`.
  `installSeed` — случайный на установку; синхронизируется с сервером в составе снапшота (PD-14).
- Позиция: клетка последнего хода лога дня. Занята — ближайшая свободная по Манхэттену, при равенстве — меньший индекс.
- Один «улёт» на дату; повторное решение той же даты (Play не считается) клетку не добавляет.
- «Решаема» — `countSolutions(подсказки, 2) === 1` (не раньше 17 клеток); показывается тихо в подписи секции. PD-120: подписи на Today
  переписаны без языка решателя — «needs more clues» / «enough clues» (uk «потрібно ще підказок» / «підказок достатньо», ru аналогично),
  под секцией строка `today.gridExplain`. Порог измерен, а не взят из концепта: единственное решение появляется при 30–69 клетках
  (медиана 42), поэтому текст говорит «30–60 за раз, по одной в день», а честного «прогресса к решаемости» нет — число клеток не
  предсказывает момент (прогресс-бар врал бы).
- Бесконечность: `nextGrid` (следующий индекс с пустым набором). UI решения Grid ∞ нет (экрана в утверждённом макете
  нет), поэтому правило «каждая следующая сетка требует больше открытых клеток» пока не применяется — открытый вопрос.

Хранение — интерфейс `ProgressRepository` (`today/repository.ts`); в приложении работает `IndexedDbProgressRepository`
(PD-14, см. «Хранение, устройство и синхронизация»), `InMemoryProgressRepository` оставлен для тестов и как
деградация (IndexedDB недоступна — приватный режим, отказ браузера: игра работает, данные живут до закрытия вкладки).

## Система движения (PD-89)

Источник — `design/pd81-motion-variants.md` (вариант 2 «Ритм»). Только `transform`/`opacity`/цвет, события, а не циклы;
ни звука, ни вибраций. Единицы — `rem`, Dynamic Type движение не ломает.

**Reduced motion — в одном месте.** `styles/tokens.css` задаёт `--mo` (амплитуда: 1 / при reduced 0) и `--mk`
(длительность: 1 / .72) и единственный `@media (prefers-reduced-motion: reduce)`. Каждая анимация умножает смещения и
масштабы на `--mo`, а длительности и стаггер на `--mk`/`--mo` прямо внутри `@keyframes`/`calc()`: при reduced она сама
превращается в короткий кроссфейд или тинт. Новую анимацию отдельным reduced-блоком не дублировать (тест
`scripts/motion-css.test.mjs`). `prefers-reduced-transparency` и `forced-colors` живут отдельно, как раньше.
Кривые: `--e-out`, `--e-spring`, `--e-ring`.

| --- | --- | --- |

## Хранение, устройство и синхронизация (PD-14)

Код — `src/sync/`. Цель: персональное (Grid ∞, решённые дни/год с карточками) переживает чистку IndexedDB;
незавершённая партия — нет (см. ниже: на сервере о ней только сводка). Приложение при этом **офлайн-first** —
регистрация и синхронизация никогда не блокируют игру.

### IndexedDB (`sync/idb.ts`, `idbRepository.ts`)

Своя тонкая обёртка без библиотек: база `pundoku` v1, хранилища `kv` (ключи `permanent` — Grid ∞, `meta:<key>` —
служебное: `meta:deviceToken`, `meta:syncState`) и `days` (ключ — дата `YYYY-MM-DD`; прогресс дня: MoveLog, заметки,
таймер, `solved`, `solvedAt`, `late`, `assisted`, источник/сложность сетки). `LazyProgressRepository` открывает базу
при первом обращении и при любом сбое открытия переключается на память (в консоли одно предупреждение).
Порядок записей держит IDB (транзакции одного хранилища); `DayStore` не читает день, пока не дописаны его записи.
Тесты — vitest + `fake-indexeddb`.

### Устройство и токен (`sync/manager.ts`)

При первом запуске без токена `SyncManager` шлёт `POST /api/devices`; `deviceToken` кладётся в IndexedDB
(`meta:deviceToken`, запись через `setMetaIfAbsent`: при гонке двух вкладок на свежем профиле локально остаётся один
токен — победителя первой записи, вторая вкладка свой токен забывает). Это гарантия только **на стороне клиента**:
обе вкладки успели вызвать `POST /api/devices`, поэтому на сервере остаётся одно устройство-сирота в `devices`
(без снапшота, токен потерян; безвредно, отдельной чистки нет). Сеть/сервер недоступны,
429 — повторы с экспоненциальной паузой (2 с → 5 мин, не короче `Retry-After`), а также по событию `online` и при
возврате видимости вкладки. Игра стартует сразу; единственное ожидание — при загрузке Today до 1,5 с
(`RESTORE_WAIT_MS`) на первичную сверку, чтобы восстановленный с сервера день/Grid ∞ не перезаписался новым
(дольше не ждём — сеть не должна тормозить игру).

**Ограничение до PD-27 (привязка e-mail):** токен лежит в том же IndexedDB. **Потеря/чистка всего IndexedDB = потеря
токена = данные без привязанного e-mail восстановить нельзя**: приложение заведёт новое устройство с пустым
состоянием, а старый снапшот останется на сервере недоступным. Чистка IndexedDB *кроме токена* (или потеря только
данных, токен жив) восстанавливается полностью — решённые дни и Grid ∞ приходят с сервера. Для снижения риска:
`navigator.storage.persist()` запрашивается при старте (`sync/runtime.ts`, результат игнорируется, ничего не
блокирует); iOS в установленной PWA обычно его выдаёт, но гарантий нет (отчёт `03-tech.md` §1).

### Снапшот `PUT/GET /api/snapshot`

Известное: на устройстве без снапшота (первый запуск и после регистрации) первый `GET /api/snapshot` отвечает
`404 snapshot_not_found` — это штатное состояние нового устройства, но браузер пишет его в консоль красной строкой.
Контракт api осознанно не менялся (404 однозначен для клиента, `200` с пустым телом размывал бы «снапшота нет» и
«снапшот пустой»); шум в консоли — известное поведение, не ошибка.

Формат `data` (`sync/schema.ts`, `SNAPSHOT_SCHEMA_VERSION = 1`):

```
{ schemaVersion: 1,
  grid: { installSeed, index, cells: [{cell, date}] } | null,        // Grid ∞
  days: { "YYYY-MM-DD": {
      status: "solved" | "unfinished",
      solvedAt?: ISO, timeMs?: number, technique?: string,            // technique — самая сложная применённая
      hadCorrections: boolean,      // из MoveLog: были исправленные/стёртые ошибочные цифры (= !summary.clean)
      corrections?: number, assisted: false,                         // подсказок нет, всегда false
      late: boolean,                // дата дня < сегодня на момент решения
      source: "sudoku.com" | "generator" | "device",                 // откуда сетка (клиентский фолбэк = "device")
      difficulty, mission,          // mission — 81 символ, чтобы восстановить партию/карточку
      heat?: string,                // тепловая карта пути: 81 клетка × 2 base36 (162 символа), `--` = не трогали
      moveLog?: string } }          // сжатый MoveLog, см. ниже; может отсутствовать (бюджет/413)
}
```

Это данные для экрана Year: цвет дня берётся из `status/hadCorrections/late/assisted/technique/timeMs` без разбора
moveLog; `heat` и сводка — постоянная часть записи. Незавершённый день хранит только сводку (`timeMs`, `mission`): поставленные цифры, заметки и ходы недоделанной
партии на сервер **не уходят**, поэтому после чистки IndexedDB они **не восстанавливаются** (вернутся только решённые
дни и Grid ∞; недоделанную партию придётся начинать заново).
Решённый день с `moveLog` восстанавливается на клиенте полностью (карточка дня — как на исходном устройстве);
без `moveLog` — из `heat` синтетическим логом (карточка с теми же цветами клеток, без последовательности ходов).
`winRate` хранится в записи дня и возвращается на карточку («N % solved today») при восстановлении и при замене
локальной записи серверной слиянием: `DayStore.resumeSaved` берёт сохранённый `winRate` независимо от `verification`
(у записи из `progressFromRecord` оно всегда `"local"`, `verification` в снапшот не входит; сам `winRate` пишется в запись
только если он относится к сохранённой сетке — при «доигрываем свою сетку» он сбрасывается, см. п. 4 таблицы сверки).
Не восстанавливается лишь `serverVerified` (ответ `false` на verify скрывал «N %» на исходном устройстве) — после
восстановления считается «нет ответа», а `winRate` показывается.
Если слияние заменило запись дня, который **уже решён на открытом экране** (Today или архив: у локального решения клиентская
сетка, у победителя — Sudoku.com с `winRate`), `DayStore.applyRemote` вызывает `reloadSolved`: экран без прохода через
«загрузку» показывает победившую запись (сетка, `winRate`, источник), а запись в хранилище не затирается проигравшей —
на время замены `persist` молчит, а обновление Grid ∞ по `gridChanged` не пишет запись дня (PD-43; раньше решённый день
оставался на экране проигравшей записью без `winRate` до перезагрузки). Тест — `today/dayStore.merge.test.ts`.

**Синхронизация.** `SyncManager` отправляет снапшот после значимых событий (день решён и улёт в Grid ∞ записан,
конец партии; ход в начатом дне лишь помечает «не синхронизировано» и уходит с ближайшей отправкой) с debounce 2 с, при возврате в сеть, при возврате видимости (GET не чаще раза в
30 с) и немедленно при уходе вкладки в фон. Сервер — источник правды для постоянной сетки и года: при первом цикле
сессии клиент делает GET и сливает. Пустое локальное + непустое серверное = восстановление из GET (`onRemoteApplied`
обновляет открытый экран). Состояние синхронизации — внешний стор `sync.manager` (`subscribe/getSnapshot`:
`device`, `phase: idle|syncing|offline|retrying|blocked`, `unsynced`, `version`, `lastSyncedAt`, `error`) —
хук под будущий индикатор «не синхронизировано» (UI не добавлялся). Ретраи идемпотентны (см. политику).

**Политика 409** (`sync/merge.ts`, покрыто `merge.test.ts` и `manager.test.ts`; сервер принимает только `version`
строго больше сохранённого, иначе `409` с текущим снапшотом в теле — клиент сливает и шлёт `version + 1`):

1. **Дни — объединение по датам** (нет с одной стороны — берём с другой).
2. **Конфликт по одному дню** (признаки строго по порядку, поэтому слияние коммутативно, идемпотентно и
   ассоциативно): «решён» над «не решён»; затем **источник сетки** — серверная сетка (`sudoku.com`, а также
   серверный `generator`) над клиентским фолбэком (`device`) **независимо от `solvedAt`** — иначе более ранний
   solvedAt фолбэк-сетки вытеснял бы настоящую сетку Sudoku.com вместе с её `winRate`/`moveLog`/`heat`; при равных
   источниках — оба решены: более ранний `solvedAt`; равенство — запись с `moveLog`, затем детерминированно по
   сериализации с отсортированными ключами (порядок ключей на результат не влияет); оба не решены — больше `timeMs`.
   `sudoku.com` и `generator` между собой считаются равными (обе — сетка, выданная сервером; сервер сам заменяет
   `generator` на `sudoku.com`, клиент всё равно сверяет `mission` при возврате в сеть).
3. **Grid ∞:** `installSeed`/`index`/набор улётов берутся с сервера, если он новее по `version` (на 409 — всегда),
   иначе с клиента; улёты второй стороны добавляются по датам (одна дата — один улёт, клетка занята — ближайшая
   свободная). Одинаковый `installSeed` и разный `index` — побеждает больший `index`. **Счётчики Grid ∞ не хранятся
   отдельно** — это длина набора улётов по датам, поэтому слияние идемпотентно.
4. Слияние идемпотентно и не теряет данные, поэтому повторы после сетевых сбоев и «потерянных ответов» безопасны.

**Миграции схемы.** `migrateSnapshot(raw, target, MIGRATIONS)` поднимает снапшот «старее → новее» цепочкой
`MIGRATIONS[n]: n → n+1` (сейчас единственная 0 → 1, каркас + тест на цепочку). Снапшот **новее** схемы клиента
(`schemaVersion > 1`) не читается и не перезаписывается: `phase: "blocked", error: "newer_schema"` (старое приложение
не должно затереть данные нового). Невалидные дни при разборе отбрасываются по одному.

**Размер и лимит 413** (сервер: 1 МиБ на `data`, JSON-парсер 1200 КиБ). MoveLog в компактном виде
(`sync/codec.ts`: ходы `клетка+цифра+тип+время`, ≈7–9 символов на ход) — измерено на партиях движка: простая
партия дня без заметок ≈ 0,4 КиБ; с заметками, отменами и исправлениями оценка 3–5 КиБ. Запись без `moveLog` —
≈ 0,5 КиБ (реально 184 КиБ на 365 дней). Полный год с `moveLog` по 3–5 КиБ — 1–1,8 МиБ, то есть упирается
в лимит, поэтому: бюджет `moveLog` ≈ 600 КиБ символов на снапшот (потолок одной партии 48 КиБ), последние 7 дней
всегда с логом, старые теряют `moveLog` первыми (остаются `heat` и сводка). Если сервер всё равно ответил 413 —
ступени сжатия: бюджет по умолчанию → только последние 7 дней → без `moveLog`. Принятая ступень (`compressStep`)
хранится в `meta:syncState` рядом с подтверждённым снапшотом и **переживает перезапуск** (иначе каждый старт при
≥ ~1500 днях делал бы два лишних PUT с 413/200 и рос `version` без изменений данных); ступень «липкая» — назад к
более полным логам не возвращается, пока запись `syncState` не сброшена (401/новое устройство); если и без логов не влезает — `phase: "blocked", error: "too_large"`. Предложение
для Year на будущее: рисовать год по `heat`/сводке (постоянная часть), а `moveLog` считать «горячим» кэшем
последних недель; для лимита выше года — вынести `moveLog` в отдельный эндпоинт/таблицу по дням.

### Формы и цвет (решения владельца 2026-09-29)

| Состояние | Метка |
|---|---|
| решён | полный квадрат (`is-solved`), чернила |
| были исправления | сургуч + сколотый правый верхний угол (`has-corr`) — факт, не число; смысл не держится на одном цвете |
| `assisted` (решено с подсказкой) | более светлый тон 62 % (`has-help`), постоянно, без переключателя; в релизе 1 всегда `false` — рендер проверен на синтетике |
| начат и брошен | нижняя половина (`is-unfinished`) |
| решён после своей даты (`late`, PD-125) | рамка с ядром (`is-late`): контур 1.5 px цветом метки + маленький квадрат в центре; сочетается со сколом угла (исправления) и тоном помощи; не пропуск и не наказание, усилие видно |
| пропуск | контур `--hairline` (`is-missed`, 1.71:1 — намеренно тихо; смысл дублируют слова в подписях дня и карточке) |
| будущее / до первой записи | пусто (`is-void`) |
| сегодня | кольцо чернил снаружи клетки (`is-today`), при отсутствии записи — на пустой клетке |

Тон/цвет: `--mark-ink`/`-soft`, `--mark-wax`/`-soft` (light, dark и `prefers-contrast: more`, значения макета);
`forced-colors` — CanvasText/GrayText/Highlight: блок `@media (forced-colors: active)` стоит **в самом конце** `year.css` (при
равной специфичности побеждает более поздний; порядок стережёт `scripts/year-css.test.mjs`), селекторы по специфичности не ниже авторских
(`.ymark.has-corr` и т. д.), все метки — `CanvasText` (смысл держат форма и скол угла), карточки месяцев, клетки дней
в шите и меню лет получают `border` системного цвета (заливки и тени система отбрасывает). Легенда всегда на экране
(кроме пустого года); подписи месяцев, дней недели и легенда — в `rem` (0.6875rem = 11 px при базовом размере),
то есть следуют Dynamic Type; легенда в en помещается в одну строку на 390/430, в uk/ru и на 320 переносится на
вторую, а при высоте экрана ≤ 600 pt интервалы уплотняются (`@media (max-height: 600px)`), чтобы легенда при первом
показе не уходила под таб-бар.

### Правила `late` и «пропусков»

- **Доигранный позже день (`late = true`) в Year — отдельное состояние «solved late» (PD-125, решение владельца 6.6;
  раньше он оставался контуром-«пропуском» и узнавался только после победы).** Знак — рамка с ядром (`is-late`, `MarkKind
  "late"`), смысл не держится на цвете (форма отличается от полного квадрата, скола угла, нижней половины и пустого
  контура; форма «исправлений» и тон «помощи» сочетаются с ним, как у решённого вовремя). `late` не пропуск: его нет в
  `missed`, он **не входит** в «N days / N clean» (как и раньше), но считается отдельно — `MonthSummary.late` /
  `YearTotals.late`, в строке итогов «· N solved late», в подписи месяца «N solved late», в легенде («Solved late»), в
  подписи дня («solved late», «solved late, with corrections», …) и карточке дня (пометка «Solved after its day — your
  year keeps it as “solved late”.»). Усилие не стирается: время, исправления, техника и тепловая карта показываются как у
  любого решённого дня. Цвет: чернила / сургуч (исправления) / светлый тон (помощь) — тот же `--m`, что у обычной метки.
  `forced-colors`: рамка `CanvasText` + ядро `CanvasText` (правило в конце `year.css`).
- **Предупреждение ДО старта (PD-125):** в карточке прошлого дня над «Play this day’s puzzle» / «Finish this puzzle»
  (`YearSheet.tsx › LateWarning`, `data-testid="late-warning"`) стоит строка со знаком «Если решишь сейчас — год сохранит
  его как “solved late”» (en/uk/ru, без обещаний про итоги: честно называет, что будет записано). Показывается ровно там,
  где есть кнопка (`archivable`), у сегодняшнего/будущего/решённого дня и до границы архива её нет. Результат архивного
  дня (`TodayScreen › late-note`) использует тот же знак и ту же формулировку состояния, что Year.
- **Смена суток в живой сессии (PD-137, находка QA по PD-125).** Приложение открыто за полночь, Today держит вчерашнюю
  партию (ходы есть — `refresh` день не подменяет) и она дорешана без перезагрузки: Year уже рисует `late`, поэтому и
  карточка результата Today показывает ту же пометку `late-note` со знаком (раньше — только в архиве) и подпись винрейта
  «N % solved that day», а не «solved today». «Сегодня» определяет не дата партии, а часы в момент первого решения
  (`DayStore.persist`: `late = date < localDate(now)`; он же пишет запись и снапшот) — признак берётся из `snap.late`,
  одинаково для Today и архива. Обычный день (решён в свою дату) и день, решённый до полуночи, но показанный после, —
  без пометки, «solved today» (`today/TodayScreen.late.test.tsx`).
- **Старт года = самый ранний РЕШЁННЫЙ день (PD-51, решение владельца 2026-09-30; уточнено PD-54).** Стартуют год решённые
  дни: решённый чисто/с исправлениями/с помощью, доигранный позже (`late`), в том числе архивный и восстановленный с сервера
  (`year/model.ts › yearStart`). PD-125 проверил и **не менял**: решённый позже день стартует год ровно как раньше
  (покрыто `model.test.ts`, «yearStart: late-solved day starts the year»; решает `entry.solved`, а не вид метки). Начатый и брошенный день (`unfinished`) рисуется как есть (нижняя половина), но год **не
  стартует**: иначе один ход на «пустом» дне (между `firstUseDate` и первой партией) сдвигал бы старт и разом превращал ~30
  дней в пропуски. Дни **до старта** — пусто (`void`); пропуск (контур) рисуется только для прошедшего дня без записи **от
  самого раннего решённого дня до вчера**. Дата первого запуска (`meta:firstUseDate`, `year/firstUse.ts`, пишет `main.tsx`
  один раз) раскраску Year не определяет.
  **Пока решённых дней нет, пропусков нет вообще** (кольцо сегодняшнего дня остаётся): `YearContext.hasRecords`
  (`year/model.ts › yearContext`; имя историческое — теперь «год стартовал», т.е. есть решённый день) — одно правило для
  полотна, подписей шита и пустого состояния. Известная мелочь: брошенный день раньше первого решённого окружён днями
  `void` с подписью «before your first entry» — копию не меняли.
- **Граница архива не менялась:** играть прошлый день можно с первого дня пользования — `YearContext.archiveStart`
  (`archiveStart`: меньшее из `firstUseDate` и самой ранней записи; нет ничего — сегодня; тот же `readUseStart`, что у
  `ArchiveScreen`/`dayStore`). Она управляет только кнопками «Play/Finish» карточки дня и диапазоном листаемых лет,
  но не раскраской: дни между `firstUseDate` и первой записью пустые (`void`), но играбельны (карточка: «Before your first
  recorded day.» + «Play this day’s puzzle»). Доиграл такой день до решения — он становится первой записью (`late`,
  знак «solved late»), и старт года сдвигается на него; пока он лишь начат и брошен, старт не двигается (PD-54).
- Подписи дня без метки (шит и карточка): «not yet» — будущее; **«nothing recorded» / «Nothing recorded for this day.»** —
  только пока нет решённого дня (года нет), для прошедших дней от границы архива (не «not played»: это слово пропуска, а
  пропусков в этом состоянии не рисуем); **«before your first entry» / «Before your first entry.»** — дни до
  самого раннего решённого дня (`labels.ts › dayStateKey`; en/uk/ru: «до первой записи» / «до першого запису»).
- **Осознанное поведение (PD-41 → PD-51 → PD-54):** первая решённая партия задним числом (игрок открыл сетку за вчера сразу
  после установки) больше не превращает дни от `firstUseDate` в пропуски: пропуски начинаются с неё. Ограничение:
  после полной чистки IndexedDB и восстановления с сервера старт года — самый ранний восстановленный решённый день.
- Итоги над полотном — нейтральные числа («N days · N clean · N with corrections»): без серий, процентов и ритма недели.
- Карточка брошенного дня: «left it with N of M cells filled in **correctly**» — M = клетки, которые игрок заполняет сам
  (без заданных), N = сколько из них стоит верно. Неверная цифра в N не входит (в отличие от «cells left» с PD-118, которое считает поставленные), поэтому
  слово «correctly» в тексте обязательно: без него «29 of 43» при 30 поставленных клетках вводило бы в заблуждение.
- Дни без ходов в Year не попадают. Незавершённые дни с другого устройства локально не восстанавливаются
  (`progressFromRecord` берёт только `solved`), поэтому после чистки такой день виден как пропуск.

### Список лет и пустой прошлый год (PD-52, PD-55)

- **Какие годы листаются (`year/model.ts › availableYears`).** Год предлагается, если в нём есть запись дня или играбельный день
  (от границы архива `archiveStart` до сегодня); текущий год есть всегда. Поэтому год `archiveStart` входит в список, пока
  сама граница не позже сегодня: дни между первым запуском и первой записью играбельны и достижимы из Year (карточка дня →
  «Play this day’s puzzle»). Годы раньше границы и первой записи не предлагаются. Граница из будущего (часы сдвинули назад) год не
  добавляет — раньше это опустошало список (`hi < lo`) и выбрасывало текущий год. Внутри диапазона годы идут без дыр (год
  между записями без единой записи остаётся, его дни — пропуски и играбельны).
- **Пустой прошлый год.** Если записи есть, но не в этом (прошлом) году, строка итогов «0 days · 0 clean» заменяется одной
  строкой `year.emptyYear` («Nothing recorded in 2025.» / «У 2025 році записів немає.» / «В 2025 году записей нет.»; без
  `aria-hidden`, читается VoiceOver). Месяцы **остаются**: дни такого года играбельны (пропуски и дни от границы архива), и убирать
  к ним доступ нельзя, а формулировка говорит только о записях и не обещает и не отрицает возможность играть. Год без записей
  при полностью пустом состоянии (записей нет нигде) — прежнее приглашение «Your year starts today» .

### Не входит в PD-25

Выбор года — только когда лет больше одного. Игра архивных дней — PD-33 (ниже).

## Архив: играть прошлую дату (PD-33)

Решение владельца: пропущенный день можно доигрывать (как архив Sudoku.com); в Year он получает отдельный знак
**«solved late»** (`late = true` в записи дня; с PD-125 — не «пропуск», см. «Правила `late`»), а ДО старта карточка дня
предупреждает об этом; карточка дня доступна и показывает результат.

**Кнопки карточки дня Year** (`year/YearSheet.tsx › DayCard`), только для прошлых дней начиная с первого дня
пользования (`date < today && date >= ctx.archiveStart`; до начала пользования, сегодня и будущее — без кнопки):

| Состояние дня | Кнопка (`data-testid`) |
| --- | --- |
| нет записи | «Play this day’s puzzle» (`play-day`), над ней предупреждение `late-warning` |
| начат и не решён | «Finish this puzzle» (`finish-day`), над ней предупреждение `late-warning` |
| решён (в т. ч. `late`) | без кнопки — карточка результата (у `late` — пометка «solved late») |

**Навигация (минимальная, без нового роутера и без четвёртой вкладки).** Адрес `#/day/YYYY-MM-DD` — экран игры дня
поверх вкладки Year (Year остаётся подсвеченной, таб-бар на месте); тап по кнопке карточки → `replaceState`, как и у
вкладок. Экран — тот же `DayView`, что у Today (поле, панель, карточка результата, жесты), в режиме `archive`: над
заголовком «Archive» кнопка «‹ Year» (44 pt, `aria-label` «Back to Year»), подпись — дата дня и сложность. «‹ Year»
ведёт на `#/year/YYYY-MM-DD`: Year открывается сразу на карточке этого дня (`initialDate`, применяется один раз, затем
адрес возвращается к `#/year`), где видно итог — начатый день с «Finish», решённый с результатом. Перезагрузка на
`#/day/…` восстанавливает экран (партия хранится по дате). Разбор адреса — `shell/tabs.ts › parseRoute`.

**Стор.** `DayStore` принимает `{ archive: true }`; глобальный `archiveStore` — отдельный экземпляр под прошлую дату
(общее хранилище `ProgressRepository`, отдельное состояние), поэтому сегодняшний день и Grid ∞ не смешиваются:
- `openArchive(date)` / `closeArchive()` (уход с экрана: сохраняет накопленное время и сбрасывает в «загрузку»);
- загрузка: сохранённая партия даты → `GET /api/daily/:date` → клиентский фолбэк `dailyPuzzle(date, difficulty)` по правилам
  PD-29 (сложность берётся только у сетки `generator`, иначе `medium`; сверка mission `reconcileDay` как у Today);
  решённый день открывается карточкой сразу, без сети;
- **дата, которой нет:** `400 future_date` / `404 not_available_yet` (`FetchedDay.status`, `today/api.ts`) и сегодняшняя/
  будущая/несуществующая дата (`isArchiveDate`) → `unavailable`: сообщение «This day’s puzzle isn’t available.» без
  кнопки повтора, фолбэк-сетка не строится (сетки ещё нет), ничего не пишется; 5xx/сеть — обычный фолбэк;
  **день раньше начала пользования** (`year/firstUse.ts › readUseStart` — `archiveStart`: меньшее из первого
  запуска и самой ранней записи; с PD-51 это граница архива, а не старт года) — тоже `unavailable`, ещё до запроса сетки и
  записи: прямой URL не открывает то, что Year не предлагает. На экране недоступной даты — только сообщение, без
  поля и цифровой панели. Карточка архивного дня подписывает win rate «N % solved that day» (не «today»);
- решение: `late = date < localDate(now)` фиксируется при первом решении (запись дня и снапшот, `sync/schema.ts`),
  `hadCorrections`/`assisted`/`solvedAt` как раньше; в Grid ∞ архивный день **не летит** (стор не держит постоянную
  сетку, `landing` всегда `null`, событие сервера `gridChanged` игнорируется);
- смена суток и `refresh` на архивном сторе только сверяют сетку по её дате (без перехода на «новый день»).

**Партия вчерашнего дня, начатая на Today и не законченная к полуночи**, остаётся в сторе Today (у неё есть ходы):
`App.playDay` в этом случае ведёт на вкладку Today, а не в архив — одну запись дня не должны вести два стора.

**Синхронизация (PD-14/PD-31/PD-37) не менялась:** `late` уже входил в `DayRecord`; слияние 409 (solved > unfinished,
sudoku.com/generator > device, ранний `solvedAt` — решённый вовремя на другом устройстве побеждает late) сохраняет `late`;
восстановление (`progressFromRecord`) возвращает `late`, winRate решённого дня восстанавливается как раньше. API не менялся
(`GET /api/daily/:date` уже отдавал прошлые даты и различал 400/404).

**Открытые вопросы владельцу:** (1) попадает ли доигранный архивный день в Grid ∞ — сейчас нет (Grid ∞ =
«последняя клетка сегодняшней сетки»); (2) кнопка есть только начиная с первого дня пользования — до него играть
нельзя. Правило PD-41 заменено PD-51 решением владельца: первая запись задним числом не порождает пропусков до себя —
старт года = самый ранний решённый день (PD-54; открытым вопросом не является). Решённый день на старте — «first record»: рисуется
как late (знак «solved late»), брошенный — как unfinished.

## Уход с Settings при показанном ключе (PD-57)

Пока ключ восстановления показан один раз и не подтверждён (проверка записи PD-142 не пройдена и не пропущена), любой уход с экрана Settings идёт через action
sheet «The key isn’t saved yet» (`RecoveryStore.guardLeave/requestLeave`): «‹ Today», вкладки и — что добавил PD-57 —
браузерное «назад», iOS edge-swipe и правка адреса (`popstate`/`hashchange`, `shell/tabs.ts › useRoute(guard)`).

- Перехват: маршрут остаётся `#/settings` (экран не размонтируется, ключ живёт только в памяти), адрес сразу возвращается на
  `#/settings` новой записью истории (`pushState`), поверх — шит. «Stay» закрывает шит, ничего не теряется. «Leave» — штатный
  уход: ключ стирается, выполняется `history.back()` и приводит в ту запись, куда пользователь шёл (предыдущую при «назад»,
  набранную при правке адреса).
- «Stay», затем «‹ Today» → «Leave» (PD-60): запись, поставленная перехватом, помнит, куда шёл пользователь (`pdHeading` в
  `history.state`). `leaveSettings` делает `history.back()`, только если это Today (случай «назад»); при правке адреса на
  другой маршрут (`#/year`) идёт на Today напрямую (`replaceState`), а не на набранный адрес. Проводка guard в `App`
  покрыта `App.guard.test.tsx`.
- Ограничение веба: **закрыть или выгрузить приложение iOS (смахнуть из переключателя, выгрузка системой) перехватить нельзя** —
  `beforeunload` в iOS-PWA не срабатывает, а `pagehide`/`visibilitychange` не позволяют показать диалог. Остаются только
  предупреждение шита при уходе внутри приложения и текст «shown one time only» на экране; ключ, показанный и потерянный так,
  восстановить нельзя; при **замене** (PD-126) это безопасно: рабочий ключ не тронут до проверки и подтверждения, новый можно выпустить заново
  («Start replacement again» в карточке «New key not confirmed»). Проверить на устройстве этот случай веб не может.
- `beforeunload` (десктопные браузеры) по-прежнему держит закрытие вкладки, пока ключ показан.

## Пакет A: ввод, счётчики, партия Play (PD-115…118)

**PD-115. Повтор цифры не стирает.** `enterDigit` на клетке, где уже стоит та же цифра, — no-op (состояние то же, лог не пишется,
undo не растёт). Стирание только Erase / Backspace / Delete. Двойной тап по паду раньше стирал верную цифру. В режиме заметок
повтор кандидата по-прежнему переключает его. Тест `play/logic.test.ts`; на Today тот же код (`GameStore.input`).

**PD-118. «Осталось N» — по поставленным цифрам** (решение владельца 6.5; раньше неверная цифра в счёт не входила, и это
косвенно выдавало ошибку — оракул). `cellsLeft` = число пустых клеток; `remaining[d]` = 9 − клеток с цифрой d (включая неверные,
не ниже 0). Что осталось «по верности» и почему:

- **«Решено»** и завершение партии — `isSettled`, как раньше (все клетки равны решению). Полная сетка с ошибкой не решена.
- **VoiceOver-пороги** (каждые 10, последние 5) — те же, но по новому счёту; при полной сетке вместо «0 cells left» один раз
  озвучивается «Grid full — something doesn’t match» (повтор не звучит, пока сетка не перестала быть полной).
- **M3 (волна по завершению строки/столбца/блока)** остаётся по верности: она и есть сигнал «тут всё верно». Это единственное
  место, где ввод прямо сообщает, что строка собрана верно, — оставлено намеренно (владелец решал про счётчики, не про волну).
- **M8 (эхо «цифра закрыта»)** — когда все девять клеток цифры d стоят **верно** и именно этим ходом (`isDigitClosed`), а не при
  нулевом остатке: девять клеток с неверной среди них эхо не запускают. Остаток на клавише при нуле приглушает клавишу и
  обнуляет число — по поставленному.
- **Year** («left it with N of M cells filled in correctly») по-прежнему считает верные: `unsettledCells` (старый подсчёт).

**PD-117a. Полная сетка с ошибкой.** При `cellsLeft === 0` и не решено строка статуса и live-регион говорят «Grid full — something
doesn’t match» (uk «Сітка заповнена — десь є розбіжність», ru «Сетка заполнена — где-то есть несовпадение»), без числа и без
указания, где ошибка. Ничего не подсвечивается (настройка «Подсвечивать неверные» отдельная).

**PD-117b. Тихие отказы.** Раньше три случая были немыми. Теперь в строке статуса (она же `aria-live`) на 2,6 с (`HINT_MS`)
появляется фраза, затем возвращается счёт: цифра без выбранной (или заданной) клетки — «Pick an empty cell first»; заметка в
занятую клетку — «Notes go in empty cells only»; цифра в клетку, стоящую чернилами (в режиме Ink), — «This cell is filled — ink
doesn’t lift». Без модалки, без анимации сверх переката M9 (при Reduce Motion — без неё). Подсказка не пишется в прогресс и не
шлёт синхронизацию (`DayStore.setTransient` → `patchQuiet`); выбор клетки и любой успешный ход её снимают. На Today она на эти
2,6 с вытесняет выбор Ink (`InkEntry`), чтобы не двоить строку. Повтор той же цифры (PD-115) отклика **не** даёт — это не отказ.
Тап по Grid ∞ (мини-доска без действий) меняет подпись под ней на «Every day you solve adds a clue here.» на 4 с (`role="status"`).

**PD-116a. Партия Play переживает перезагрузку / вытеснение PWA.** `play/store.ts`: запись `meta:playGame` в IndexedDB (kv, тот же
`PersistentStore`, что у Today), формат `SavedPlay {v:1, difficulty, startedOn, play (поле/заметки/undo-стек/лог/ink/mission/solution),
elapsedMs, selected, notesMode}`. Пишется при каждом изменении `play`/фазы, при сворачивании (`visibilitychange: hidden`, `pagehide`)
и при решении; при старте приложения `playStore.restore()` поднимает партию (таймер продолжается с `elapsedMs`; пока запись
читается, `PlayScreen` не мигает экраном выбора сложности — `snap.restoring`). Завершённая партия лежит на экране результата до
явной «New puzzle»; «New puzzle»/`toSetup`/`newGame` стирают запись. **Play не попадает в синхронизацию и не в Year**: снапшот и
Year строятся из `days` (`listDays`), а Play лежит в `kv`. Битая/чужая версия записи игнорируется (старт с экрана выбора).
Без IndexedDB (jsdom, приватный режим) — деградирует в память, как остальное хранилище. Раньше «перезагрузка = новая партия» (PD-14).

**PD-116b. «New puzzle» вместо select.** Нативный `<select>` сложности из тулбара убран (случайный тап терял партию). Кнопка
«New puzzle» (≥44 pt, 16 px) ведёт на экран выбора сложности; если в партии есть ходы (лог не пуст, заметки тоже ход) — сначала
шит «Discard current puzzle?» (Discard — деструктивная / Keep playing; Esc и тап по подложке = Keep playing; стиль и компонент —
`recovery/ActionSheet`). Без ходов и после решения подтверждения нет. Цифры с клавиатуры при открытом шите игнорируются
(`handleGameKey` пропускает `[role="dialog"]`).

**PD-116c. «Watch your solve» после Play.** Таймлапс не требует даты дня (`hasTimelapse`/`timelapseOf` читают лог), нужен был только
проп `timelapse` у `ResultCard`; дата — подпись и имя PNG `pundoku-<дата старта>.png` (у Play нет дня; при решении Today и Play в
один день имена файлов совпадут — браузер добавит « (1)»). Партия после перезагрузки сохраняет лог целиком, поэтому кнопка доступна
и после восстановления.

## Замена ключа восстановления без потери старого (PD-126)

«Replace key» больше не гасит рабочий ключ при нажатии. Клиент (`recovery/api.ts`, `store.ts`, `SettingsScreen.tsx`):

- Шит «Replace the recovery key?» не деструктивный (кнопка «Make new key»): `rotate` возвращает `{key, pendingId, expiresAt}`, стор
  входит в фазу `shown` в режиме `replace` (заголовок «Your new key», текст «current key keeps working until you check and confirm it»).
- Подтверждение в режиме замены (после проверки записи, PD-142) — запрос `POST /key/rotate/confirm` с `pendingId` (busy, `aria-busy`). Успех → ключ и метка стираются,
  статус «New key is active. The old one no longer works.» (`role="status"`). Сеть/сбой/лимит → ключ остаётся на экране, ошибка с
  `role="alert"`, можно нажать снова. После сети/сбоя результат считается неизвестным (ответ мог потеряться уже после переключения):
  текст «can’t tell yet whether the new key is already active… repeating is safe», повтор безопасен — сервер идемпотентен по
  `pendingId` и ответит успехом (F1); «Leave» после такой ошибки перечитывает статус, чтобы карточка не врала. `409` (отменена/перезапущена/истекла) → ключ стирается, текст «That replacement is no longer valid».
  В режиме создания подтверждение по-прежнему только стирает ключ из памяти.
- Уход без подтверждения («Leave» в шите про *новый* ключ, закрытие приложения, перезагрузка): ключ и `pendingId` стираются (в IDB и
  `localStorage` не пишутся), рабочий ключ жив. После возврата `GET /api/recovery` отдаёт `pendingRotation` → карточка «New key not
  confirmed» со сроком («Valid until …»), кнопки «Start replacement again» и «Cancel replacement» (`DELETE /key/rotate`); строка
  «Replace key» на это время скрыта.
- i18n: добавлены `settings.key.yourNewKey`, `shownOnceReplace`, `warnReplace`, `footReplace`, `replacedOk`, `pending*`, `errConfirm*`,
  `errStale`, `sheetReAgainMsg`, `sheetLeaveRe*`; изменены `sheetReMsg`, `sheetReGo`, `footDanger` (PD-88: «подключённые устройства остаются
  подключёнными» сохранено). Паритет и `{{when}}` проверяет `recovery/i18n.test.ts`.

## Проверка записи ключа восстановления (PD-142, H-21/SC-08)

После показа нового ключа (создание **и** замена) кнопка «I’ve written it down» ведёт не к «Готово», а на шаг «Check your copy»:
два случайных поля «Group N of 8» (две разные группы, порядок по возрастанию; жребий — при каждом входе на шаг, `pickCheckGroups`).
Состояние живёт в `RecoveryStore` (`check: {groups, values, wrong}`, фаза остаётся `shown`) и **только в памяти**: значения
не логируются и не пишутся в IDB/`localStorage`; на экране проверки самого ключа нет.

- Нормализация — правила ключа (`normalizeGroupInput`): регистр, пробелы, дефисы не важны, `O→0`, `I/L→1`, `U→V`; если вставлен
  целый ключ (≥ 32 знаков), берётся запрошенная группа — пароль-менеджер/буфер не мешают. Сравнение — `groupMatches`.
- Неверно → мягкая ошибка (`role="alert"`, текст «That doesn’t match…»), `aria-invalid` только у неверного поля, остальные
  введённые значения остаются (правка поля снимает ошибку); «Show the key again» возвращает к тому же ключу (`backToKey`, фокус
  на ключе, введённое стирается), следующая проверка спросит группы заново; повторов без счётчика и блокировки (проверка
  локальная и ничего не защищает, это самопроверка).
- **Порядок относительно серверного confirm (замена): проверка раньше confirm, целиком локально.** Пока проверка не пройдена или
  не пропущена, сервер не тронут: старый ключ работает, новый ожидающий не принимается (проверено вживую через `redeem`,
  `design/pd142-shots.mjs`). Идемпотентный confirm и `pendingId` PD-126 не менялись: после прохождения вызывается тот же
  `confirmRotation(pendingId)`. Обратный порядок (confirm, потом проверка) отвергнут: он активирует ключ, который человек ещё
  не проверил, и убивает старый, а при провале проверки возвращать нечего.
- Обхода нет: публичного «подтвердить без проверки» в сторе больше нет (`confirmSaved` стал приватным `finish()`), пропуск —
  только из шага проверки через шит `skip`.
- **Пропуск разрешён и честный** (решение: жёсткий барьер превращает полезную самопроверку в стену, люди с ключом в менеджере
  паролей или с уже сделанной фотографией уйдут в «Leave»/смахивание, и ключ потеряется ещё надёжнее; PD-57/126 уже оставляют
  выход). Кнопка «Skip the check» вторична, под основной, под ней сноска: «You can skip it, but without a written-down key progress
  can’t be restored on another device.» Шит «Skip the check?» повторяет это предупреждение (для замены — ещё и «old one will
  stop working»), главная кнопка шита — безопасная «Check the key» (`destructive: true`, фокус по умолчанию на ней, H-22),
  деструктивная — «Skip the check».
- Поля: фокус в первое поле при входе на шаг (эффект в `SettingsScreen`, не `autoFocus`-атрибут), `autocapitalize="characters"`, `autocorrect/autocomplete="off"`,
  `spellcheck=false`, менеджеры паролей отключены (`data-1p-ignore`, `data-lpignore`), `enterkeyhint` next/done (Enter в последнем
  поле = «Check»), шрифт `max(18px, 1.06rem)` (iOS не зумит), высота ≥ 48, остальные цели ≥ 44, у каждого поля `label` с номером группы,
  ошибка и подсказка связаны через `aria-describedby`. AX3, 320 pt, Reduce Motion и `forced-colors` покрыты
  `scripts/key-check-css.test.mjs` и живым прогоном.
- i18n (en/uk/ru): `settings.key.written` (раньше `saved`), `verify*`, `sheetSkip*`; формулировки «Key saved» → «check and confirm»
  в `shownOnceReplace`, `warnReplace`, `footReplace`, `pending*`.
- Не сделано сознательно: экран «Готово» на сервере не помечает, пройдена ли проверка (сервер ключа не знает и знать не должен).
  Метрики пропусков нет (аналитики в продукте нет).
- **Известное поведение: перезагрузка PWA до показа ключа (создание).** Первый выпуск ключа действует на сервере сразу, а не после
  проверки (серверного «ожидающего» шага у создания нет, он есть только у замены). Если PWA перезагрузилась/вытеснилась, пока ключ
  ещё не показан, человек его не видел, а ключ уже действует и нигде не записан. Лечится
  «Replace key» (выдаёт новый ключ уже по схеме замены: ожидающий, проверка, подтверждение). Поведение было и до PD-142, проверка
  записи его не меняет (она стоит после показа и сервер не трогает).
- **AX3 / 320×568 (проверено вживую, `design/pd142-shots.mjs scroll`, кадры `wk-*-320x568-AX3-0[89]/1*`).** Шаги показа ключа,
  проверки (в том числе с ошибкой и в режиме замены) и «ключ создан» прокручиваются так, что нижний элемент шага (кнопки
  «Check» / «Skip the check» / «Show the key again», сноска) выводится выше таб-бара и нижнего inset (нижний отступ даёт `.scroll`:
  `72px + var(--sa-bot)`; конец страницы с запасом ≥ 30 px над таб-баром). Шит пропуска/замены (`.st-asheet`, `max-height: 92%`)
  прокручивается внутри, последняя кнопка выше нижнего inset. Правок CSS не потребовалось: на кадре QA страница была просто
  остановлена на полпути, следующий раздел виден сквозь стекло таб-бара.
- **Известные мелочи (Low, в бэклоге):**
  (a) при двух неверных группах сообщение «That doesn’t match…» не называет, какая именно (подсвечиваются оба поля через
  `aria-invalid`, но текст общий; при одной неверной — тот же текст, поле видно по подсветке);
  (b) кириллические двойники латинских букв (А, В, Е, К, М, Н, О, Р, С, Т, Х и т. п. из ru/uk-раскладки) при вводе молча
  отбрасываются, как и в поле целого ключа (`normalizeGroupInput` оставляет только алфавит ключа); человек с русской раскладкой
  видит укороченную группу и получает «не совпало» без объяснения.

(цель касания — вся строка), футер секции привязан `aria-describedby`. Макет — `design/pd27-settings.html` (+ §9 в `pd27-settings-notes.md`).

- **По умолчанию ВЫКЛ у всех**, включая игравших до PD-112: ключа нет — значит выкл, миграции «сохранить прежнее поведение» нет.

- **Хранение — локально** (`settings/prefs.ts`, как язык `pundoku.locale`): UI-предпочтение устройства, не прогресс; схема снапшота
  синхронизации не менялась, старый клиент ничего не затрёт. Без `localStorage` (приватный режим) — память до перезагрузки.

  цифры (в том числе неверные), так что неверная цифра больше ничем себя не выдаёт, пока настройка выключена.

## Заметки: автоочистка, «Fill candidates» и заливка ряда/столбца/блока (PD-119, PD-124)

Решения владельца 6.2 и 6.4 (`research/usability-2026-10/heuristic.md`); находки A2, A4. Две настройки — рядом с PD-112 в Settings → «Game»,
обе **ВКЛ по умолчанию** (ключа нет — вкл; выкл — значение `"0"` в `localStorage["pundoku.autoClearNotes"]` / `["pundoku.highlightPeers"]`,
`settings/prefs.ts`, тот же механизм, что у PD-112, снапшот синхронизации не затронут).

**Автоочистка (PD-119).** Постановка цифры убирает её из заметок клеток той же строки/столбца/блока (`enterDigit(..., autoClear)` →
`clearPeerNotes`). Зависит только от того, что стоит на доске, а не от верности цифры — иначе «заметки не тронулись» выдавало бы ошибку
(оракул). **Один ход — один шаг undo:** запись стека получает клиентское поле `also: [клетка, заметки до хода][]`, `undo` восстанавливает
основную клетку и их одним шагом. **Лог ходов не менялся** (ход в нём один — `place`; `summary`, `heatmap`, `timelapseFrames` движка и формат
синхронизации прежние; заметки движок в расчёты не берёт), `undoStack` хранится как раньше (IndexedDB/`localStorage`), валидатор
`isUndoEntry` (`today/repository.ts`) принимает `also`/`fill`, старые записи без них валидны.

**«Fill candidates» (PD-119)** — отдельное действие, не автоматика: в каждую пустую клетку **без заметок** пишутся все цифры, допустимые по
доске (`candidatesOf`: заданные + цифры игрока, верные и неверные; решение не используется — это факт о доске, не подсказка). Клетки с
ручными заметками не трогаются. Один шаг undo откатывает всё; в логе — один служебный `note_add` (чтобы стек клиента и стек движка
оставались зеркальными), запись undo помечена `fill: true` (откат не уводит выбор на «первую затронутую» клетку). Итог — в строке статуса
и озвучке: «Notes filled in N cells» (`play.hint.filled`, plural en/uk/ru) или «Nothing to fill in»; если остались пустые клетки без единого кандидата (тупик из-за неверных цифр, `deadEndCount`) — дописывается «; M cells have no candidates» (`play.hint.dead`, PD-143). **Где вызвать:** долгий тап (500 мс)
по «Notes» → шит «Fill candidates» (`ActionSheet`, действие сверху, «Cancel» отдельно; тап, закончивший долгое нажатие, не переключает
режим заметок; «хвост» этого жеста — указательный click до нового нажатия внутри шита — не жмёт «Fill»/«Cancel» и не закрывает шит по затемнению
(`ActionSheet guardTail`, QA PD-143 D1; клавиатура/Esc без задержки)); то же — правая кнопка мыши/контекстное меню и клавиша **F**; обнаруживаемость — подпись в футере настройки автоочистки.
Не 4-я кнопка в ряду (при 320 pt три кнопки ≥ 44 уже занимают ряд) и не «⋯» (шапка Play заполнена: «New puzzle» + шестерёнка), зазор
между полем и панелью — статус. Шит нужен как подтверждение намерения: случайный долгий тап ничего не заполняет.

**Ink (PD-71):** заметки ручные — автоочистка не действует (логика игнорирует флаг), `fillCandidates` — no-op, долгий тап по Notes ничего не
открывает. Подсказок в чернилах нет.

**Заливка соседей (PD-124)** пересматривает «соседи не заливаются» макета PD-7: клетки ряда/столбца/блока выбранной (кроме неё самой) получают
класс `.cell.peer` (`Board.tsx`, `peersOf`) и слой `.fl` с непрозрачностью `--fill-peer` (**≈3 % чернил**: light 0,03, dark 0,06 — на #1C1C1E 4 % почти не
отличались от клетки; вместе с ним в dark «та же цифра» 0,12 вместо 0,10, `more` 0,045/0,06) — отдельный токен, не `--fill-same`, чтобы подсветка подсказок PD-139 не слилась с ним. Правило в `play.css` стоит ДО
`.same`/`.sel` и использует тот же слой: заливки не складываются, «та же цифра» (10 %) и выбор (16 % + кольцо) перекрывают peer; форма ошибки
(уголок, PD-122) — отдельный `::after`, с peer не пересекается. `forced-colors`: слой гасится (`opacity: 0`), выбор держит кольцо; Reduce
Transparency не затрагивается (плоский тон, не материал). Контраст — `scripts/contrast-check.mjs` (живая клетка-сосед + пары токенов во всех
четырёх темах: цифра игрока 6,05–7,32, сургуч 5,74–7,11, заметки 4,84–13,25, заданная 15,7–16,3 — пороги не менялись). Работает и в ink
(это ориентир, а не подсказка).

## Ориентация: ландшафт в установленной PWA (PD-132)

Решение владельца: ландшафт **запретить** (только портрет), двухколонник и заглушку «поверните телефон» не делать. Что сделано:
`manifest.orientation = "portrait"` (`vite.config.ts`; Android/Chrome-PWA этому следуют; тест манифеста — `scripts/manifest.test.mjs`).
**Чего это не гарантирует на iPhone, и почему программной заглушки нет:**

- MDN/BCD: `orientation` в манифесте и `screen.orientation.lock()/unlock()` — Safari и Safari на iOS **не поддерживают**
  (`manifests/webapp/orientation.json`: `safari.version_added = false`; `api/ScreenOrientation.json`: `lock`/`unlock` — `false`).
- Исходники WebKit (trunk): манифест разбирает `orientation` с 2023 (`ApplicationManifestParser::parseOrientation`, только значение для
  embedder SPI `_WKApplicationManifest`), но `screen.orientation.lock()` скрыт настройкой `ScreenOrientationLockingAPIEnabled` (по
  умолчанию `false`, статус «testable») и, даже включённый, требует полноэкранного режима. В заметках к Safari 26.0 об ориентации ничего нет.
- Значит программно запретить поворот в установленной iOS-PWA нельзя; соблюдает ли Home Screen web app манифест на устройстве владельца
  — по документам не установить. Без стенда с iPhone утверждать нельзя: пункт 21 в `research/usability-2026-10/ios-owner-steps.md`
  (повернуть телефон в установленной PWA и сказать, остаётся ли портрет; если поворачивается — как выглядит).
- Запасные варианты, если iOS повернёт (на решение владельца/PM): (1) двухколонная ландшафтная вёрстка PD-127 (доска слева ≤ высоты
  экрана, пад справа); (2) дешёвая правка — ограничить доску `min(100cqi, 100dvh − …)` и дать прокрутку (AX-03). Заглушка «поверните
  телефон» отвергнута владельцем.

## Лесенка подсказок (PD-139, макет `design/pd133-hint-ladder.md`)

UI поверх движка `nextHint` (`packages/engine`). Состояние — `play/hintStore.ts` (`HintLadder` без React + хук `useHintLadder`), док —

- **Где доступно.** Today, Play и **архив** (прошлая дата, в т.ч. `late`) — да. **Ink-дни** и **Grid ∞** — подсказок нет вообще
  (лампочки нет; Ink нельзя включить после подсказки). Это решения владельца, не недоработка.
- **Ступени.** 1 область → 2 техника → 3 клетки → 4 разбор; «Ещё шаг» ведёт вниз, на 4-й — «Понятно». Две ветки без лесенки: «ошибка на

  Закрытие на ступени ≥3 выбирает клетку шага. В ru/uk «clue» в Grid ∞ везде «клітинка/клетка», «подсказка» — только hint.
- **Метка «с помощью».** Ставится ПЕРВЫМ результативным открытием (шаг или ошибка); «ничего не нашёл» и `beyond` не помечают. Счёт
  `hints` растёт на каждое результативное открытие дока. Предупреждение ДО: одноразовый шит правила (флаг `pundoku.hintRule` на
  устройстве, плюс «уже были дни с подсказкой») и постоянная строка в подвале дока. Строка-намёк «Stuck?» — один раз на устройство
  (`pundoku.hintNudge`): ≥90 с без поставленной цифры, ≥5 пустых, шаг существует.
- **Хранение, без миграции схемы.** `DayProgress.assisted` (булево, было всегда), `DayProgress.hints?` (опционально, у старых записей 0)
  и `PlayState.hintLog?: {t, cell|null}[]` (опционально; валидируется в `dayProgressProblem`). `hints` и `hintLog.length`
  растут вместе. `hintLog` в снапшот сервера **не уходит**: на другом устройстве карточка покажет метку/счётчик без засечек таймлапса.

- **Перезагрузка** закрывает док (`hints`/`assisted` уже в записи, ступень — нет).
- **Year.** Метка «с подсказкой» (форма, не только цвет) и строка легенды «With help»; в карточке дня строка о подсказках.
- **Результат.** Карточка партии Play несёт «с помощью» (Play в Year не попадает). PNG-отпечаток: «N подсказок» в подписи, без
  техник и клеток (спойлер-фри). Таймлапс: засечки подсказок на шкале и строка в сводке.
- **Раскладка.** Док занимает место панели 1–9, доска не двигается (проверено 393×852). На низких экранах (SE 320×568) док выше свободного
  места: он прокручивается в видимую область над таб-баром (`scroll-margin`), шапка при этом уходит вверх. На AX3 док прокручивается
  внутри себя, ступень открывается сверху. Play-вариант шита и подвала (в т.ч. ветки «ничего не нашёл») говорит про игру, Today/архив — про день.
- **«Чисто» в Year (решение владельца: «с помощью» — не чистый день).** `buildYear`: `clean` = решённые вовремя дни без исправлений И
  без `assisted`; день с подсказкой и правками вычитается один раз. Рядом счётчик `withHelp` (строка итогов «N with help», подпись
  месяца «… N with help»), пересекается с «with fixes». `late` в `clean`/`withHelp` не входят. Карточка дня и результат остаются

- **Синхронизация подсказок (известное ограничение).** В снапшот сервера уходят `DayRecord.assisted` и `DayRecord.hints` (число

## Today: док подсказки без сдвига, продолжение партии, холодный старт (PD-147)

- **Скорость старта ветерана (a).** Регрессия «0.46 → 0.93 с» как свойство сборки не воспроизвелась: при одинаковой нагрузке машины `a6b9088` и `main` дают одно и то же в пределах шума (раньше сравнивали прогоны подряд при разном load average; честный замер — только чередованием сборок, `research/usability-2026-10/today-fix/bench-today.mjs`). Старт целиком упирается в CPU (разбор бандла, рендер, первая отрисовка), а доска у ветерана ждёт восстановления с сервера и затем цепочку «чтение записи → запрос сетки дня». Сжата цепочка, лишнего кода не убрано: `dayStore.ensureStarted()` вызывается из `main.tsx` до монтирования React (маршрут по `readRoute`), запрос сетки дня идёт параллельно ожиданию восстановления (`prefetchDay`: для решённого дня и архива сети нет), `SyncManager.boot()` читает метаданные и `collectLocal` параллельно, а запись слитого снапшота не стоит на пути к первому кадру (`integrate(remote, deferPersist)`, ждётся после `initialDone()`). Замер (WebKit 393x852, ветеран, 12 прогонов, сборки чередовались, load average 6–21): `a6b9088` холодный 0.67 / p90 0.91 с, тёплый 0.60 / 0.96; после правок холодный 0.61 / 0.94, тёплый 0.55 / 0.85. Цель ≈0.45/0.40 на этой машине недостижима (минимумы 0.46–0.50 при нагрузке); остаток — разбор и выполнение бандла.
- **Док подсказки на Today (b).** Today в партии — тот же нескроллящийся экран `.play-fit` и тот же резерв `--extra` (`.play-hintable`, `.play-docked`), что и Play (PD-144); классы собирает общая `fitClassName` (`play/fitModel.ts`), дублей нет. Док занимает место панели; доска и заголовок не двигаются на ступенях 1–4 и в ветках «ошибка»/«не нашёл» (`design/today-fix-check.mjs`: 320×568, 375×667, 390×844, 393×852; en/uk/ru, светлая/тёмная, AX3; Today и архив). Карточка «решено» остаётся прокручиваемой. Для укладки в одну строку шапки и зазора: заголовок не переносится (uk/ru — не больше 11vw), строка «Ink mode» компактнее (сноска и при AX3 подпись — только для скринридера), строка источника при AX3 — тоже; в архиве ряд «‹ Year» входит в обвязку (`--bar`).
- **Продолжение партии (c).** `resumeSelection` (`play/logic.ts`): первая ПУСТАЯ клетка (раньше — первая не-заданная, у начатой партии она уже заполнена и первый ход стоил двух касаний); в Play сохранённый курсор остаётся, пока его клетка пуста; пустых нет — выбора нет. Повторный тап по той же цифре не стирает (PD-115).
- **404 `/api/snapshot` (d).** Только что зарегистрированное устройство снапшот не запрашивает (`registeredNow` в `SyncManager.cycle()`): на сервере для нового токена его быть не может, а браузер пишет 404 в консоль, как бы ни был обработан код. Следующие запуски тянут снапшот как раньше (восстановление и PD-126/142 не затронуты). Остаток: профиль, который зарегистрировался, но ничего не выгрузил (только своя сетка в Play), на втором запуске получает один 404 — безопасно убрать нельзя (потеря локального состояния синхронизации после удачной выгрузки, PD-126).
- Живые проверки: `design/today-fix-check.mjs`, `design/today-fix-resume-check.mjs`. iPhone-пункты — `research/usability-2026-10/ios-owner-steps.md`, раздел Л.

## Режим «Лжец» (PD-171, план `docs/release2-modes-plan.md` §1)

Строка «Лжец» в списке «Режимы» (реестр `play/modes.ts`, `grid: "liar"`). Одна из данных подсказок ложна; сетка — `generateLiar` /
`dailyLiarPuzzle` движка в том же Worker (`play/generate.worker.ts`, запрос `liar: true`).

- **Секрет партии** — `PlayState.liar` (`liarCell`, `liarDigit`, `trueDigit`, `honestMission`) + `PlayState.accusations`
  (`Accusation[]`, не ходы лога). UI читает только производные `play/liar.ts`: `liarHidden` (каналы ответа закрыты),
  `acquittedCells` (вердикты сделанных обвинений), `caughtLie` (после поимки). **До поимки** нет подсветки ошибок по
  решению (`Board`), лесенки подсказок (`GameStore.hintAllowed`), волн M3/M8 (`GameStore.input`); `Move.correct` считается,
  но не выводится; Ink несовместим (`setInkMode`, `GameStore.setInk`). Тест утечек — `liar.ui.test.tsx`: две партии с одним
  полем и разными секретами рисуются байт-в-байт одинаково; живая проверка — `design/pd171-shots.mjs` (a11y-дерево, HTML, URL, консоль).
- **Обвинение** — долгое нажатие / контекстное меню на подсказке → меню с одним пунктом «Обвинить» (`AccuseMenu`, визуальный
  язык меню строки режима PD-167). Тот же путь — «⋯ → Обвинить эту цифру…» (выбрана подсказка) и клавиша A: для VoiceOver и
  клавиатуры; подпись клетки-подсказки заканчивается «press and hold to accuse». Верно: клетка получает истинную цифру
  (`mission`), ложь зачёркнута в углу, печать сургучом; включаются подсветка ошибок и подсказки. Неверно: печать контуром
  («оправдана»), повторно обвинить нельзя (и в UI, и в `canAccuse`/`accuseCell`). Решено = все клетки верны И лжец пойман.
- **Карточка** — строки «Ход обвинения», «Обвинения» (с первого раза / N неверных), «Пойман на» и сравнение с собой: средний
  ход обвинения по другим пойманным партиям устройства (`meta:liarHistory`, не синхронизируется). **Таймлапс** — слой
  обвинений по `moveIndex` (`liarTimelapseLayer`): обвинение видно с последнего кадра перед ним.
- **Лжец дня** (medium) — строка «Лжец дня» в шите режима над сложностью; незаконченный — строка «Продолжить» хаба. Запись
  `meta:liar:YYYY-MM-DD` (не слот: переживает решение), свободная партия — слот `playGame:liar`. Снапшот: необязательный раздел
  `liar` (`sync/liarSchema.ts`): `status, solvedAt, timeMs, difficulty, mission` (с ложью), `caught, catchPlacement, catchT,
  wrongAccusations, firstTry, accusations, moveLog` (свой бюджет логов — 1/10 общего). Нет Лжеца дня — раздела нет, снапшот
  байт-в-байт прежний; схема не версионируется. Слияние — атомарная запись дня (`pickLiarRecord`). С сервера пишется только
  решённый и только если локально его нет решённым; секрет при восстановлении выводится из `mission` (`validateLiar`).
  Year: пойманный Лжец дня — точка-печать в правом нижнем углу клетки дня (цвет клетки — качество классики), строка в карточке дня.
- **Генерация** — всегда в Worker с потолком ожидания (`GENERATION_TIMEOUT_MS`: 15 с easy–hard, 45 с expert/master → «Не
  удалось» с повтором). expert/master заготавливаются заранее (`play/liarPool.ts`): при входе в режим (шит Лжеца) и сразу
  после старта партии, по одной на класс в `meta:liarReady:<класс>`, в своём Worker, с таймаутом 30 с; заготовка чужой
  `LIAR_VERSION` выбрасывается. Нет заготовки — «Готовим сетку…» до конца генерации.

## Мелодия: звуковое ядро и слот (PD-201, план `docs/release2-modes-plan.md` §4, без UI)

UI — PD-203 (раздел ниже).

- **Звук — `src/melody/audio.ts`**, только синтез Web Audio, без файлов. `createMelodyAudio(opts?) → MelodyAudio`:
  `unlock()` (вызывать из обработчика жеста; создаёт/резюмирует `AudioContext`), `attachUnlock(target = document)` (вешает
  `unlock` на pointerup/touchend/click/keydown, capture), `playNote(digit)`, `playUnit(digits, delayMs?)` (арпеджио, шаг 110 мс),
  `playPath(events, { onStep, onEnd, fromMs })` → `{ stop(), done }` (события `melodyOf` движка, `t` — шкала таймлапса;
  новый вызов останавливает предыдущий; шаги идут и без звука — синхронизация с таймлапсом), `setMuted`, `setTimbre`,
  `state()` (`locked | running | suspended | unsupported | disposed`), `dispose()`. `scheduleNote(ctx, out, digit, at, timbre)`
  — одна нота (годится для `OfflineAudioContext`).
- **Ноты:** цифра 1–9 → мажорная пентатоника по возрастанию от C4: C4 D4 E4 G4 A4 C5 D5 E5 G5 (`noteFrequency`). Громкость
  тихая (`DEFAULT_VOLUME` 0.18, пик сигнала ≈ 0.1). Огибающая: 0 → пик за ≥ 5 мс → экспоненциально к тишине → 0 — без щелчков.
- **Тембры (`TIMBRES`):** `marimba` «Дерево» (по умолчанию — выбор владельца PD-202), `soft` «мягкий синус», `bell` «колокольчик» (негармоничный обертон ≈ 2.76),
  `marimba` (треугольник + обертон ×4, короткий хвост). Меняются только числа пресета.
- **iOS:** до жеста контекста нет и ноты молчат (`false`); перед созданием контекста `navigator.audioSession.type = 'ambient'`
  (iOS 17+: уважает беззвучный режим, не глушит чужую музыку); прерывание (звонок, сон PWA → `interrupted`/`suspended`) —
  тишина без ошибок, следующий жест резюмирует; закрытый системой контекст пересоздаётся; отказ `resume()` глотается.
- **Слот и флаг:** режим `melody` в реестре (`play/modes.ts`); слот `playGame:melody`,
  `PlayState.melody: true` (`setMelodyMode`, строгий разбор слота, граница хранилища дня), `DayRecord.melody: true` (санитайзер,
  восстановление, слияние атомарно) — по прецеденту `glyphs`. Значок и тексты `modes.melody.*` — из макета PD-163.
- **Dev-стенд (не в сборке):** `npx vite --port 5201 --strictPort` → `http://localhost:5201/dev/melody.html` (кнопки нот,
  арпеджио, путь дневной easy, mute, тембр); живая проверка chromium + webkit — `design/pd201-audio-check.mjs`.
