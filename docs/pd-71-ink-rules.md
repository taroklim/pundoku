# PD-71 — Чернильный режим: правила (engine/store, без UI)

Релиз 1.1. UI ждёт утверждённый макет владельца; здесь — только правила, данные и хранилище. Все решения ниже —
рекомендация PM, владелец ещё подтвердит, поэтому смена решения сделана дешёвой: **правила живут в одном модуле**
`packages/engine/src/ink.ts` (`INK_RULES`, `inkAllows`, `inkViolations`), остальной код их только применяет.

Рамка из `reports/sudoku-pwa-research/07-concept-draft.md` (решение 7): режим строго opt-in, явное правило на входе,
никогда не дефолт, без отмены и ластика, ошибка = клякса.

## 1. Правила

| # | Правило | Где реализовано |
| --- | --- | --- |
| 1 | Ошибка = `place` с цифрой ≠ решению. Неверная цифра — **клякса**: в лог идёт ход `place(wrong, correct:false, blot:true)`, клетка блокируется и (флаг `autoReplaceBlot`, по умолчанию `true`) тут же, в тот же `t`, получает верную цифру ходом `place(right, correct:true, blot:true)`. Партия всегда завершаема. | `play/logic.ts › inkBlot`, флаг — `INK_RULES.autoReplaceBlot` |
| 2 | Каждая клякса = **1 correction** и **1 mistake** в сводке; `hadCorrections = true` (через `!summary.clean`). | `engine/movelog.ts › replay` |
| 3 | `undo` в ink-партии недоступен — отвергается логикой (`undo` возвращает то же состояние), стек undo не ведётся. | `inkAllows("undo")`, `logic.undo` |
| 4 | Цифру стереть нельзя: ни `eraseCell`, ни повторное нажатие той же цифры (в обычной партии это стирание). Заполненная клетка (верная или клякса) заблокирована, перезапись тоже отвергается (перезапись = скрытое стирание). | `inkAllows("place"/"erase")`, `logic.enterDigit/eraseCell` |
| 5 | Заметки (`note_add`/`note_remove`) разрешены как раньше; в заполненной клетке не ставятся (как и в обычной партии); `erase` пустой клетки = очистка заметок — разрешён. Флаг `INK_RULES.allowNotes`. | `inkAllows("note_*")`, `logic.toggleNote` |
| 6 | Режим выбирается **до первого хода** (первый ход = первая запись в лог, заметка тоже) и после неизменен в обе стороны. До первого хода его можно включить и выключить. | `logic.setInkMode`, `GameStore.setInk` |
| 7 | Только Today и Play. Архивные дни — нет (`INK_RULES.allowInArchive = false`; флаг на случай решения владельца). Постоянная сетка Grid ∞ — нет (там нет ввода игрока: клетка «приземляется» из решённого дня). | `DayStore.inkAllowed` |
| 8 | Возобновление после закрытия PWA сохраняет ink и кляксы: `PlayState.ink` и лог живут в `DayProgress.play`, который `DayStore` пишет в хранилище на каждое изменение партии. Откатить перезагрузкой нельзя — старый стор состояния ink-партии не хранит. | `DayStore.persist` (без изменений), тест `dayStore.ink.test.ts` |

`cellsLeft`/`remaining`/«решено» в ink считают клетку **закрытой**, если она верна либо в ней стоит любая цифра игрока
(неверная цифра в ink бывает только кляксой при `autoReplaceBlot = false`). Это не зависит от текущего значения флага —
партия, записанная при одном его значении, корректно читается при другом.

## 2. Контракт лога (для таймлапса, PD-70)

Обратно-совместимое расширение `Move`: опциональное `blot?: boolean` (`engine/types.ts`). Старые логи читаются как
раньше, обычные логи не меняются.

Ошибка в ink даёт ровно два хода с одним `t` и одной клеткой:

```
{ t, cell, kind: "place", digit: <неверная>, correct: false, blot: true }   // клякса
{ t, cell, kind: "place", digit: <верная>,   correct: true,  blot: true }   // авто-замена (нет при autoReplaceBlot=false)
```

Как воспроизвести кадр: на первом ходе клетка показывает кляксу с цифрой `digit`, на втором (в ту же миллисекунду) —
верную цифру; время «настоящей» постановки клетки — `t`. В ink-логе **нет** `undo`, `erase` цифр и `place` в
заполненную клетку; `erase` встречается только для очистки заметок пустой клетки. `inkViolations(log)` проверяет это и
возвращает список нарушений (пусто = лог чистый). Хелперы: `blotsOf(log)` (кляксы: клетка, цифра, `t`), `isBlotMistake`,
`isBlotMove`.

`replay` движка (`heatmap`, `summary`, `solvingStyle`) работает с новым логом без спец-случаев для undo; таймлапс,
идущий по обычному `replay`, видит клякса→замена как «поставили неверную — перезаписали верной».

Кодек снапшота (`sync/codec.ts`): признак `blot` кодируется в символе `correct` (`4` blot+верная, `3` blot+неверная,
`2` blot без `correct`), а **лог, содержащий хотя бы один blot-ход, пишется с новым префиксом `2:`** (находка PD-70:
старый декодер на неизвестный вид хода возвращает `null`, и `sanitizeDayRecord` молча выбрасывает `moveLog`; с новым
префиксом старый клиент честно «не видит» лог, а не читает его неправильно). Любой другой лог — в том числе ink-партия
без ошибок — по-прежнему `1:` байт-в-байт; новый клиент читает оба префикса, а символы `2`/`3`/`4` под `1:` считает
повреждением. Тесты: `sync/ink.test.ts`, мутанты «always 1:» и «blot chars under 1:» убиваются.

### Почему `Move.blot`, а не «только `correct:false` + отсутствие undo»

Координатор предложил обойтись без расширения `Move`. Проверено: счёт corrections без флага совпал бы (ход-клякса 0 +
авто-замена поверх неверной +1 = 1), но без флага (а) лог не отличить от обычной партии «ошибся и перезаписал» — нельзя
ни проверить контракт (`inkViolations`), ни отрисовать кляксу в таймлапсе, ни исключить авто-замену из `placements`/
`solvingStyle` (иначе «змейка» и `evenness` считают её постановкой игрока); (б) при `autoReplaceBlot = false` клякса без
замены не давала бы correction вовсе. Поле опциональное, читатели без знания о нём видят обычный «неверный ход + перезапись»,
поэтому PD-70 (`timelapseFrames`) должен работать на ink-логе без правок (проверить тестом при ребейзе на main после мержа pd-70). Если владелец предпочтёт минимальный вариант — убрать `blot` можно ценой
этих трёх потерь (ВОПРОС ВЛАДЕЛЬЦУ не нужен, это техническое решение, фиксируется здесь).

### Версия схемы снапшота — решение

`SNAPSHOT_SCHEMA_VERSION` **остаётся 1** (требование тикета). Цена: клиент до PD-71 санитайзером срежет неизвестные `ink`/`blots`
при следующем push дня — то есть ink-пометка дня на сервере может потеряться, если после неё день перезапишет старый
клиент. Бамп до 2 защитил бы (старый клиент ушёл бы в `blocked: newer_schema`) с тождественной миграцией `1 → 2`, но
блокирует единственного реального клиента (владельца) до обновления, а обновляется он деплоем — поэтому риск принят.
Если поле окажется критичным (например, значок в Year), решение пересматривается одной константой + тождественной
миграцией; сейчас `ink` — информационное поле, день и его цвет восстанавливаются и без него по `corrections`.

## 3. Данные

- `PlayState.ink?: boolean` (`play/logic.ts`) — опционально; нет поля = обычная партия. Кляксы отдельно **не хранятся**:
  единственный источник — лог (`blotsIn(play)`).
- `DayRecord.ink?: true` и `DayRecord.blots?: number` (`sync/schema.ts`) — только у ink-дней (у обычного дня полей нет,
  запись побайтно прежняя). `blots` нужен сводке и переживает бюджет `moveLog`; каждая клякса уже входит в `corrections`.
- **`SNAPSHOT_SCHEMA_VERSION` не менялась** (остаётся 1): поля опциональные, старые записи без `ink` = `false`,
  миграция не нужна. `sanitizeDayRecord` принимает только `ink === true` и целое `blots` 0..81 (и только вместе с `ink`).
- `progressFromRecord`: восстанавливает `play.ink`; если `moveLog` не влез в бюджет, `logFromHeat` строит синтетический
  лог с настоящими парами клякса→замена (по числу `blots`, на первых по времени клетках), поэтому `summary` даёт те же
  `corrections`/`mistakes`/`clean`, и в нём нет «поставил/стёр» (их в ink не бывает).
- Выбор ink до первого хода пишется в хранилище (день без ходов в **снапшот на сервер** не попадает — как и раньше).
  Замена сетки дня серверной до первого хода (`reconcileDay: replace`) выбор сохраняет.

## 4. Влияние на метрики движка

| Что | Поведение в ink |
| --- | --- |
| `summary.corrections` | +1 за кляксу (ровно; авто-замена новой правки не добавляет). Одинаково при `autoReplaceBlot` true/false. |
| `summary.mistakes` / `clean` | +1 за кляксу; день с кляксой не `clean`; ink без ошибок — `clean`, как обычный чистый. |
| `summary.placements`, `evenness`, `intervalVariance`, `maxTechnique` | авто-замена **не постановка игрока**, игнорируется: у ink-дня `placements` = число пустых клеток (как у обычного). Постановка кляксы учитывается (игрок выбрал клетку и цифру). Техника у клякс не размечается. |
| `solvingStyle` | по действующим постановкам игрока; авто-замена исключена (иначе «змейка» получала бы дубль клетки). |
| `heatmap` | клетка-клякса закрашивается моментом авто-замены (верная цифра); при `autoReplaceBlot = false` — `null` («так и не заполнена верно»). |
| `winRate` Sudoku.com | для ink-дня показывается как есть (режим на него не влияет; серверная проверка решения как обычно — в сетку уходят итоговые верные цифры). |
| Year | красит по тому же правилу: клякса = исправление (`hadCorrections`), без нового цвета. Ink без ошибок = чистый. Форма метки (`solved`/`unfinished`/`missed`) не меняется. |

## 5. Крайние случаи

- **Клякса на последней клетке:** лог оканчивается парой blot, партия `solved`, `cellsLeft = 0`; клетка приземления
  Grid ∞ — клетка последнего хода (клякса) — как обычно. Тест: `play/ink.test.ts`.
- **Заметки в заблокированной клетке:** не ставятся (как в обычной партии в клетке с цифрой); в момент постановки цифры
  (в т. ч. кляксы) заметки клетки гаснут; вернуть их нельзя (нет undo).
- **Заметка как «первый ход»:** после неё режим фиксируется. Рекомендация: так проще всего объяснить и не даёт «разогреться»
  в обычном режиме и переключиться. (ВОПРОС ВЛАДЕЛЬЦУ №4.)
- **Возобновление:** см. правило 8. Play (свободная игра) партию не сохраняет вообще (PD-14: «перезагрузка = новая партия»),
  поэтому возобновление относится к Today.
- **Новая партия в Play:** режим не переносится (никогда не дефолт); на каждую партию выбирается заново.
- **Архив:** `setInk(true)` отвергается архивным стором; архивная запись с `ink` (если она пришла с другого устройства
  и флаг позже включат) читается нормально.
- **Повторное нажатие той же цифры** по заполненной клетке в ink — no-op (а не стирание).
- **Два устройства, слияние по дню с разным `ink`** (409 и восстановление): запись дня **атомарна**, поля `ink`/`blots`/
  `moveLog`/`heat`/`corrections` никогда не смешиваются. Побеждает существующее правило — «решён» > «не решён»,
  серверная сетка > клиентской, затем **более ранний `solvedAt`** (первое решение дня — настоящее), при неравных
  незавершённых — больше `timeMs`. Поэтому `ink` победителя не теряется, а ink-день, решённый позже обычного, уступает
  (как и любое второе решение дня). Слияние остаётся коммутативным/идемпотентным (тесты `sync/ink.test.ts`).

## 6. ВОПРОС ВЛАДЕЛЬЦУ (рекомендации — по умолчанию уже реализованы)

1. **Авто-замена кляксы верной цифрой** (`INK_RULES.autoReplaceBlot`). Рекомендация — `true`: партия всегда завершаема,
   клякса = «ошибка, которая остаётся следом». Альтернатива `false`: неверная цифра остаётся на поле навсегда, клетка
   считается закрытой (счёт тот же, сетка визуально «грязная» — честнее, но итоговая сетка неверна, а серверная проверка
   решения — `verify` — тогда даст «не совпало»). Переключение — одна константа.
2. **Архивные дни** (`INK_RULES.allowInArchive`). Рекомендация — `false`: ритуал дня, не тренажёр. Включить — одна константа.
3. **Слияние двух устройств с разным `ink`:** рекомендация — первое решение дня побеждает (как сейчас). Альтернатива:
   «ink сильнее» (ink-запись побеждает независимо от времени) — сохраняет достижение, но позволяет чистому обычному
   решению вытесниться ink-решением с кляксами в Year. Оба варианта — правка одного признака в `pickDayRecord`.
4. **Заметка считается первым ходом** (режим фиксируется после неё). Альтернатива — считать первым ходом только цифру.
5. **Заполненная верная клетка тоже заблокирована** (нельзя перезаписать) — следствие «нет ластика»; уточнить, нет ли
   желания разрешить править верную цифру (обычно нет).
6. **Показывать ли ink-пометку на карточке дня / в Year** (значок, строка «N blots») — данные (`ink`, `blots`) есть,
   решение по UI — за макетом.
