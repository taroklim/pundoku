# PD-27 — ключ восстановления (ADR, план; заменяет вариант с e-mail)

Решение владельца (2026-09-30): **почты не будет вообще, e-mail не делаем** (выбор «e-mail в
настройках» был случайным). Вместо этого — **ключ восстановления** (recovery key): без почты, без
аккаунтов, без паролей, без экранов входа. Игра работает без входа, как сейчас; ключ — необязательная
опция в Settings.

Зачем: (1) новое устройство подтягивает прогресс; (2) восстановление после потери IndexedDB/токена
устройства (README web: после полной чистки данных сайта прогресс без ключа недоступен).

## Идея
Токен устройства НЕ подменяется: у каждого устройства остаётся свой `deviceToken`. Ключ
восстановления — секрет, по которому устройство **присоединяется к группе синхронизации**, т.е.
меняется только то, чей снапшот оно читает/пишет. Логика `upsertIfNewer`/409/слияния PD-14/PD-31
остаётся как есть.

## Ключ
- 20 случайных байт (160 бит, CSPRNG) → Crockford base32 (32 символа, без I/L/O/U), показ группами
  `XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX` (8×4). Слов (12 words) не используем — не нужен словарь.
- Ввод нормализуется: пробелы/дефисы убираются, регистр не важен, `O→0`, `I/L→1`.
- Сервер генерирует ключ и показывает **один раз** в ответе создания/перевыпуска; в БД — только
  `HMAC-SHA256(key, RECOVERY_KEY_HMAC_SECRET)`. Сам ключ на сервере не хранится и не логируется.
- Потерянный ключ не восстановить; перевыпустить можно с любого присоединённого устройства. С PD-126
  **замена отложенная**: новый ключ только выдаётся как «ожидающий» и сам ничего не ломает; старый ключ
  перестаёт работать в момент подтверждения (confirm), которое клиент отправляет только после проверки записи ключа (PD-142: ввод двух групп, либо явный пропуск с предупреждением; всё локально). См. «Замена ключа (PD-126)».
- Ключ даёт доступ к прогрессу (в снапшоте нет персональных данных, только ходы судоку) — в UI это
  сказано прямо, хранить как пароль.

## Модель данных (миграция `apps/api/migrations/0006_sync_groups.sql`)
- `sync_groups(id uuid pk, key_hmac bytea unique not null, snapshot_device_id uuid not null
  references devices(id), key_created_at timestamptz, created_at timestamptz)`.
- `device_links(device_id uuid pk references devices(id) on delete cascade, group_id uuid not null
  references sync_groups(id) on delete cascade, linked_at timestamptz)`.
- Снапшот группы лежит в `snapshots` под `sync_groups.snapshot_device_id`. Резолв в `requireDevice`:
  `snapshotOwnerId = device_links → sync_groups.snapshot_device_id, иначе device.id`. Репозиторий
  снапшота работает с `snapshotOwnerId`; `upsertIfNewer`/409 без изменений.
- Группа создаётся только при создании ключа; «группа» = «есть ключ».
- PD-126 (миграция `0007_sync_groups_pending_rotation.sql`, только nullable-колонки, совместима с рабочей БД):
  `sync_groups.pending_key_hmac bytea`, `pending_id uuid`, `pending_expires_at timestamptz`; CHECK «все три заданы
  или все NULL» и `octet_length(pending_key_hmac)=32`. Одна ожидающая замена на группу.
- F1 (миграция `0008_sync_groups_confirmed_id.sql`): `sync_groups.confirmed_id uuid` (nullable) — метка замены, сделавшей
  рабочим ТЕКУЩИЙ ключ; пишется в одном `UPDATE` с `key_hmac` при confirm, поэтому всегда описывает именно рабочий ключ.

## Эндпоинты (все под `requireDevice`, Bearer токен устройства)
- `POST /api/recovery/key` — создать ключ. Если устройство уже в группе → `409 key_exists`. Иначе
  создаёт группу (`snapshot_device_id` = это устройство: его снапшот становится снапшотом группы),
  линкует устройство, отвечает `201 {key, devices:1}` — ключ показывается **один раз**.
- `POST /api/recovery/key/rotate` — только для устройства в группе (иначе 404 `no_key`): **начинает** замену.
  `200 {key, pendingId, expiresAt}` — ключ один раз; в БД только его HMAC как `pending_*` (TTL 24 ч). Старый
  ключ **продолжает работать**, новый **не принимается** redeem'ом, пока не подтверждён. Повторный rotate
  затирает прежнюю ожидающую замену.
- `POST /api/recovery/key/rotate/confirm` `{pendingId}` — подтверждение после проверки записи (PD-142): атомарно (одна транзакция под
  блокировкой строки группы) `key_hmac := pending_key_hmac`, `key_created_at := now`, pending очищается.
  `200 {confirmed:true}`. **Идемпотентно (находка QA F1, миграция `0008`):** повтор с меткой замены, которая уже сделала
  текущий ключ рабочим (ответ на первый confirm потерялся) — `200 {confirmed:true, alreadyConfirmed:true}` без изменений.
  Ошибки: `400 invalid_pending` (не UUID), `404 no_key`, `409 no_pending` (нечего
  подтверждать/уже подтверждено/отменено), `409 pending_replaced` (метка не совпала: замену перезапустили с
  другого устройства), `409 pending_expired`. Метка `pendingId` нужна, чтобы устройство не подтвердило ключ,
  которого не видело.
- `DELETE /api/recovery/key/rotate` — отменить ожидающую замену (идемпотентно, `200 {pending:false}`). Лимит — отдельный
  от confirm (30/ч каждый), чтобы после `429` на confirm замену всё равно можно было отменить.
- `POST /api/recovery/redeem` `{key}` — присоединить это устройство к группе. Успех: `200
  {linked:true, devices:n}`. Любая неудача (неверный, перевыпущенный, удалённый ключ, кривой формат)
  — **один и тот же** `400 invalid_key`, без различий по причине и по времени (поиск по HMAC, без
  раннего выхода по формату кроме длины). Если устройство уже в этой группе — идемпотентный успех;
  если в другой — сначала выходит из неё (как unlink ниже), потом присоединяется. Собственный
  прежний снапшот устройства остаётся сиротой, не удаляется. После успеха клиент вызывает
  `SyncManager.resetAfterLinkChange()` (см. Web) — слияние локальных дней с снапшотом группы.
- `GET /api/recovery` → `{hasKey:false}` или `{hasKey:true, devices:n, keyCreatedAt, pendingRotation:
  {expiresAt}|null}` (истёкшая ожидающая замена не показывается; самого ключа и метки там нет).
- `DELETE /api/recovery/link` — «отвязать это устройство»: удаляет его `device_links`. Устройство
  получает **копию** текущего снапшота группы как собственный (не теряет серверную копию). Если оно
  было владельцем снапшота и в группе остались другие устройства — снапшот группы переезжает на одно
  из них (`UPDATE` device_id + `sync_groups.snapshot_device_id`; в одной транзакции). Если было
  последним — группа удаляется (ключ погашен).
- `DELETE /api/recovery` — «удалить ключ и разорвать все связи»: удаляет группу и все `device_links`
  (ключ погашен). Снапшот группы достаётся устройству, выполнившему действие (ему переезжает
  строка); остальные устройства возвращаются к своим собственным снапшотам (их локальные данные
  никуда не деваются, на следующей синхронизации они выгрузят их сами). Локальные данные
  устройств не трогаются.

## Безопасность
- Высокая энтропия (160 бит) → офлайн-перебор бессмыслен, но лимит на попытки обязателен:
  `redeem` — по IP (in-memory, как остальные, 20 неудач/час) и по устройству (10 неудач/час, счётчик
  по `device_id`); создание/перевыпуск — 5/час на устройство. Превышение — `429`.
- Ответ на неверный ключ одинаков (`400 invalid_key`), без утечек «ключ существовал раньше».
- Ключ и `Authorization` — в `pino redact` (тело запроса `key`, ответ создания/перевыпуска тоже не
  логируем); в логи — только `groupId`, `keyHmacPrefix` (первые 6 hex) и результат. `pendingId` — тоже секрет-ручка:
  не логируется.
- `RECOVERY_KEY_HMAC_SECRET` — обязателен вне dev (≥32 байт, иначе `ConfigError` без стека), в dev
  допустим дефолт с предупреждением.
- Внешних зависимостей и почтового транспорта нет.

## Web
- Маршрут `#/settings` + шестерёнка в шапке Today (таб-бар остаётся 3 вкладки). Язык — там же.
- Состояния блока «Ключ восстановления»:
  1. Ключа нет → «Создать ключ восстановления» + «У меня есть ключ».
  2. Ключ показан один раз: группы по 4 знака, «Скопировать», предупреждение «показывается один раз,
     храни как пароль», подтверждение «Я сохранил ключ» (до него закрытие/уход — с предупреждением).
  3. Ключ создан: «Устройств: N», «Заменить ключ» (PD-126: шит не деструктивный, «Создать новый ключ»;
     текущий ключ работает, пока не подтверждён новый; уже подключённые устройства остаются подключёнными —
     шит говорит об этом прямо, PD-88), «Отвязать это устройство», «Удалить ключ и разорвать все связи»
     (деструктивное подтверждение).
  3a. Замена (PD-126): «Ваш новый ключ» (показ один раз, пояснение «текущий ключ работает, пока вы не проверите и не подтвердите его»), «Я записал ключ» ведёт на проверку двух групп (PD-142), успешная проверка (или пропуск) подтверждает на сервере (busy; при сетевой ошибке/лимите ключ
     остаётся на экране, можно нажать снова; при 409 — ключ стирается и объясняется, что замена устарела).
     После успеха «Новый ключ действует. Старый больше не работает».
  3b. «Новый ключ не подтверждён»: если игрок ушёл («Leave»), закрыл/перезагрузил приложение, новый ключ
     потерян (показывается один раз), но текущий жив. В блоке — карточка со сроком действия и действиями
     «Начать замену заново» и «Отменить замену»; строка «Заменить ключ» на это время скрыта.
  4. Ввод ключа на новом устройстве (`autocapitalize=characters`, `autocomplete=off`, ≥16px, вставка
     из буфера, авто-форматирование по 4 знака).
  5. Ошибки: неверный ключ (единый текст), лимит попыток.
- После успешных redeem / unlink / rotate(нет) / revoke: `SyncManager.resetAfterLinkChange()` —
  сбросить `META_SYNC_STATE`, `pulled=false`, `syncNow(true)`: `integrate` при `state===null`
  смержит снапшот группы с локальными днями, дальше штатный цикл/409. Токен устройства не меняется,
  локальные данные не теряются.
- i18n en/uk/ru, паритет ключей проверяется тестом (как у Year). Ключ не пишется в IndexedDB
  постоянно и не попадает в логи консоли; после подтверждения «сохранил» из памяти стирается. `pendingId`
  тоже живёт только в памяти стора; после перезагрузки клиент знает о замене лишь из `GET /api/recovery`
  (`pendingRotation.expiresAt`) и подтвердить её не может, только отменить или начать заново.

## Замена ключа (PD-126)
Причина: исследование юзабилити SC-08 / H-21 / C4 — «Replace key» гасил рабочий ключ в момент нажатия;
если игрок не успел или не смог записать новый (закрыл приложение, iOS выгрузил PWA), он оставался без
ключа. Теперь переключение происходит только по подтверждению.
- Состояния группы: `active` (есть `key_hmac`) + необязательный `pending` (`pending_*`, TTL 24 ч).
- `rotate` → pending; `confirm(pendingId)` → pending становится активным; `cancel`, повторный `rotate`,
  истечение TTL, отвязка последнего устройства и удаление ключа (CASCADE группы) гасят pending.
- Pending-ключ **нельзя** предъявить в `redeem`: пока игрок не подтвердил, действует только старый.
- Гонки (проверены на Postgres): confirm против redeem по старому/новому ключу, параллельные confirm,
  confirm против нового rotate, против cancel/delete — выигрывает ровно одна из сторон, состояние
  непротиворечиво (строка группы блокируется `FOR UPDATE`, `key_hmac` перепроверяется после ожидания).
- Развёртывание: клиент без PD-126 (закэшированная PWA), вызвав новый `rotate`, получит ключ, который никогда
  не станет активным (он не знает confirm); старый ключ при этом остаётся рабочим. Ломается только эта
  замена, потерь доступа нет.
- **Потерянный ответ confirm (F1, QA PD-138).** Запрос дошёл и переключил ключ, а ответ оборвался: клиент видел «нет
  соединения», повтор получал `409 no_pending` и текст «замена устарела, текущий ключ работает», хотя новый ключ уже
  действует, а старый мёртв. Решение — идемпотентность на сервере: повтор confirm с `confirmed_id` группы → `200`
  (`alreadyConfirmed`). Почему не «клиент сверяет статус»: из `GET /api/recovery` нельзя точно узнать, что активный ключ —
  именно этот (`keyCreatedAt` — время, а не идентичность; другое устройство могло подтвердить свою замену в тот же момент,
  и клиент показал бы ложный успех — ровно та беда, что чиним). Точное сравнение метки на сервере ложного успеха не даёт.
  Безопасность не ослаблена: повтор не меняет состояние, требует знания случайного UUID (его видел только тот, кому
  вернули ответ rotate; в `GET` он не отдаётся), работает только в группе вызывающего устройства (чужая группа/без группы —
  как раньше `404`/`409`), следующая подтверждённая замена затирает `confirmed_id` (прежняя метка → `409`), удаление ключа
  уничтожает метку вместе с группой. Окно по времени не вводили: метка не «давность», а идентичность рабочего ключа, и
  ответ «уже подтверждено» остаётся правдой, пока ключ не сменили. `pendingId`/ключ по-прежнему только в памяти клиента,
  не в storage и логах (в логе — только флаг `alreadyConfirmed`). Клиент: сеть/сбой при confirm помечают результат
  «неизвестен» (текст «пока не ясно, действует ли уже новый ключ… повтор безопасен»), повтор даёт успех; «Leave» после
  такой ошибки перечитывает статус с сервера. Лимит `429` и 401 отсекаются до обработчика — там confirm не выполнялся.
  Остаточный случай: после потерянного ответа другое устройство успело подтвердить свою замену — повтор получит `409`,
  и это правда (новый ключ этого устройства уже заменён).
- «Подтверждение» остаётся самоаттестацией («я сохранил»). Усиление из H-21 — ввести 1–2 группы нового
  ключа — не делали; кандидат на следующий тикет.
