# PD-70 — Таймлапс своего прохождения: данные и воспроизведение

Релиз 1.1. Здесь — исследование (хватает ли лога, вес, потери при слиянии, схема) и то, что сделано без UI
(UI ждёт утверждённый макет владельца). Замеры — `packages/engine/scripts/timelapse-measure.ts`
(воспроизводятся: `pnpm --filter @pundoku/engine build && pnpm --filter @pundoku/api exec tsx ../../packages/engine/scripts/timelapse-measure.ts [seedOffset]`).

## Итог в пяти строках

1. **Текущего лога достаточно**: `place/erase/note_add/note_remove/undo` + `t` воспроизводят путь целиком, Move расширять не нужно.
2. **Паузы в `t` уже не содержат «свёрнутого приложения»**: таймер стоит, пока страница скрыта или вкладка не на экране; остаются только
   «подумал/оставил экран включённым» — их сжимает `maxGapMs` в `timelapseFrames`.
3. **Вес**: сжатый `moveLog` — в среднем ≈ 1,6 КиБ на партию (без заметок 0,65, с лёгкими 0,85, с «карандашом по всем клеткам» 3,3; p95 ≈ 4 КиБ).
   Бюджет 600 КиБ вмещает ≈ 385 средних дней; для игрока без/с лёгкими заметками — 700–950 дней; для «тяжёлых заметок» — ≈ 185.
4. **Бюджет можно оставить как есть**: локально (IndexedDB) лог хранится целиком и навсегда, Таймлапс смотрят на устройстве; сервер — бэкап
   на случай потери устройства, для этого «последние ≈ 6–12 месяцев» достаточно. Если владелец захочет «все дни после восстановления» — см. варианты ниже.
5. **Схема снапшота не меняется** (`SNAPSHOT_SCHEMA_VERSION = 1`, новых синхронизируемых полей нет). Найден и исправлен пробел: синтетический лог из `heat`
   после restore уходил в снапшот как настоящий `moveLog` (см. § в).

## а) Хватает ли лога

Клиент (`apps/web/src/play/logic.ts`) пишет на каждое действие `Move { t, cell, kind, digit?, correct?, technique? }`; стек undo клиента зеркалит стек
движка один в один (README движка, «Контракт undo»). Для воспроизведения нужны ровно эти поля:

| Нужно для кадра | Откуда |
| --- | --- |
| цифра в клетке | `place.digit` |
| верность (клякса) | `place.correct` (иначе сверка с решением) |
| заметки | `note_add/note_remove.digit`; `place`/`erase` чистят заметки клетки; `undo` возвращает цифру **и** заметки клетки как до действия (клиент хранит `prevNotes`) |
| откат | `undo` — по стеку движка; `cell`/`digit` undo-хода информационные |
| время | `t` — мс **активного** времени партии |

Проверено: кодек `sync/codec.ts` без потерь для этих полей (round-trip `decode(encode(log)) == log` на 180 сыгранных логах замера; `t` целое).

**Паузы и сворачивание PWA.** `GameStore.syncClock`: часы идут только при `phase === "playing"`, вкладка Today/Play на экране и
`document.visibilityState === "visible"`. Сворачивание приложения, смена вкладки, блокировка экрана — **не** попадают в `t`
(накопленное `elapsedBase` сохраняется в IDB и продолжается после перезапуска; `t` не убывает — `stamp()`). Значит, длинные разрывы `t` — только реальные
«думал / отвлёкся при включённом экране». Начало отсчёта — загрузка партии, поэтому первый ход может сильно отстоять от нуля. Все такие разрывы
(включая «старт → первый ход») `timelapseFrames` режет порогом `maxGapMs` (по умолчанию 3 с).

Не хватает (и не нужно для 1.1): нет маркеров «сессий» (перезапуск приложения, возврат из фона) — для таймлапса они не нужны; нет события выбора клетки
(курсор) — таймлапс показывает поле, а не пальцы.

**Чернильный режим (PD-71).** Move расширять для таймлапса не нужно: «без отмены» — отсутствие `undo`-ходов (кадры их и так не требуют), «ошибка = клякса» —
`place` с `correct: false`, который остаётся в `wrong` кадра до перезаписи/стирания. Режим партии логично хранить полем дня (`DayRecord.mode?: "ink"`,
опционально), а не полем хода. Если PD-71 добавит новый `MoveKind` или поле хода, то: (1) `timelapseFrames` нужно научить новому виду (сейчас неизвестные виды не
создают кадров — `switch` без ветки), (2) кодек должен сменить префикс формата `1:` → `2:` (см. § г, почему).

## б) Вес

60 партий на каждый из трёх прогонов (3 × 60 = 180; сводка ниже — первый прогон, два других в пределах ±3 %): сетки всех 5 классов движка
(`generate`), 4 стиля порядка постановок (scanner / blocker / snake / sniper) × 3 профиля заметок (none / light — заметки у ≈ 30 % клеток /
heavy — кандидаты во всех пустых клетках сразу + чистка соседей при каждой постановке), вероятностные паузы (лог-нормальные шаги, 4 % долгих пауз
40–400 с), ошибки (≈ 5–15 %, стирание/undo/перезапись), undo верных цифр. Игрок синтетический — порядок величин, а не статистика по людям.

| Срез | ходов (среднее) | символов `moveLog` (среднее / p95 / max) | символов на ход |
| --- | --- | --- | --- |
| все 60 | 168 | 1 592 / 3 914 / 4 067 | 9,5 |
| заметки none | 64 | 643 / 813 / 836 | 10,0 |
| заметки light | 85 | 831 / 1 078 / 1 144 | 9,8 |
| заметки heavy | 354 | 3 304 / 4 035 / 4 067 | 9,3 |
| стили scanner / blocker / snake / sniper | 160–174 | 1 524–1 644 | 9,5 |
| easy … master | 112 … 199 | 1 063 … 1 890 | 9,5 |

Стиль размер не определяет; определяют **заметки** (≈ 80 % ходов «карандашного» игрока — `note_add/note_remove`) и сложность (число пустых клеток).
Ни одна партия не приблизилась к потолку `MOVE_LOG_MAX_CHARS` (48 КиБ): максимум 4 КиБ. Сырой JSON того же лога — в среднем 9,4 КБ (кодек ≈ 5,9×
компактнее).

**Сколько дней влезает в бюджет `MOVE_LOG_BUDGET_CHARS` = 600 КиБ** (последние 7 решённых дней — сверх бюджета всегда):

| Профиль | символов/партия | дней в бюджете | год (365) | 3 года |
| --- | --- | --- | --- | --- |
| без заметок | 643 | ≈ 955 | 229 КиБ | 0,67 МиБ |
| лёгкие заметки | 831 | ≈ 740 | 296 КиБ | 0,87 МиБ |
| среднее по замеру | 1 592 | ≈ 385 | 568 КиБ | 1,66 МиБ |
| «тяжёлые» заметки | 3 304 | ≈ 185 | 1 178 КиБ | 3,45 МиБ |
| p95 партии | 3 914 | ≈ 156 | 1 395 КиБ | 4,09 МиБ |

Остальная запись дня без лога ≈ 0,5 КиБ (год ≈ 184 КиБ), лимит сервера на `data` — 1 МиБ. То есть **хранить всё** в текущем формате безопасно для года
при лёгких/без заметок (≈ 230–300 + 184 КиБ), при средней нагрузке — впритык (≈ 750 КиБ), при «тяжёлых» заметках — не влезает, а через ≈ 1,5 года не влезет и у среднего.

**Варианты**

| Вариант | Эффект (по замеру) | Цена |
| --- | --- | --- |
| A. **Оставить бюджет** (рекомендуется) | ≈ 385 дней в среднем, 185 у «тяжёлых»; локально — всё | ничего; дни за пределами бюджета после wipe возвращаются без таймлапса (только heat-карточка) |
| B. Поднять бюджет (напр. до 800–850 КиБ) | +33…40 % дней; потолок — 1 МиБ минус записи дней (≈ 184 КиБ/год + сетка) | меньше запаса до 413 при росте числа дней; ступени 413 всё равно срежут |
| C. Хранить всё | не влезает при средней нагрузке через ≈ 1,5 года | постоянные 413 → ступень «7 дней» для всех |
| D. gzip/brotli поверх кодека | gzip+base64 ≈ 0,72× (brotli+b64 ≈ 0,59×); год при среднем — 410 КиБ вместо 568 | base64 съедает треть выигрыша (jsonb-строка, не blob); декодирование через `DecompressionStream` (iOS ≥ 16.4) — доп. асинхронность в синхронном `sanitize`; сложнее отладка |
| E. **Отрезать заметки у старых логов** (например, старше 30 дней) перед подгонкой под бюджет | средний лог 0,65 КиБ вместо 1,6 (heavy: 3,3 → 0,66): бюджет вмещает ≈ 940 дней у любого профиля | **нельзя вырезать просто `note_*`**: `undo` заметки тогда начнёт отменять соседнее действие — нужна стриппинг-функция с прогоном стека (выбросить note-ходы и те `undo`, что их отменяли). Таймлапс по умолчанию заметок не показывает (`opts.notes = false`), так что потери для него нет |
| F. Отдельный эндпоинт/таблица логов по дням | снимает лимит 1 МиБ совсем | изменение api + синхронизации; на 1.1 — избыточно |

Рекомендация: **A для релиза 1.1**; если на практике (реальные владельцы с «карандашным» стилем) упрёмся в 413-ступени — **E**, затем **B**. D/F — только при росте сверх нескольких лет.

**Вес кадров.** Кадры — данные в памяти, не хранятся: ≈ 170 кадров на партию (с заметками), 81 число на кадр; строятся за миллисекунды.

## в) Потери лога при слиянии 409 и restore

Где лог живёт: локально — `DayProgress.play.log` (структурный клон в IDB, **полный, без бюджета**); в снапшоте — `DayRecord.moveLog` (сжатая строка, **только у `solved`**;
`sanitizeDayRecord` не читает `moveLog` у `unfinished`, `dayRecordFromProgress` его не пишет).

| Ситуация | Что происходит с логом | Достаточно ли |
| --- | --- | --- |
| Обычный push | Локальные записи полные, `buildSnapshotData` срезает по бюджету **копию** для сервера; локальный лог не трогается | да |
| 409, оба решили **один и тот же** день (тот же `solvedAt`) | тай-брейк `pickDayRecord`: запись с `moveLog` побеждает | да |
| 409, один и тот же день решён **двумя разными партиями** (два устройства) | побеждает более ранний `solvedAt` целиком (с логом победителя); лог проигравшей партии теряется, а локальная запись затирается (`applyLocally`) | по дизайну («первое решение — настоящее»); таймлапс второй партии потерян |
| 409, локальный `device` (клиентский фолбэк) против серверной сетки | серверная сетка побеждает независимо от `solvedAt`; лог партии на фолбэк-сетке теряется | по дизайну |
| Restore после wipe IDB (токен жив / ключ восстановления) | приходят логи, влезшие в бюджет сервера; остальные решённые дни — только `heat` + сводка → `logFromHeat` | **частично**: без таймлапса остаются дни за бюджетом |
| Сервер ответил 413 | ступени 600 КиБ → 7 дней → без логов, ступень «липкая» навсегда (локально лог цел) | достаточно, но «навсегда» — 1 раз упёрлись, и серверные логи старше недели не вернутся |
| Незавершённая партия | на сервер уходит только сводка | достаточно для 1.1 (таймлапс — только для решённых) |

**Найденный пробел (исправлен).** Restore дня без `moveLog` собирал `DayProgress` с синтетическим логом (`logFromHeat`: каждая клетка верной цифрой один раз,
время по `heat`, правки парами «поставил/стёр» в `t = 0`). Следующая же сборка снапшота (`dayRecordFromProgress`) кодировала этот лог как настоящий `moveLog`,
и он уходил на сервер — в лучшем случае бесполезный, в худшем принимался бы Таймлапсом за настоящий путь (и побеждал урезанную запись при слиянии — «запись с `moveLog`»).
Исправление: `PlayState.logSynthetic?: true` (ставит `progressFromRecord`, когда `moveLog` не декодировался), `dayRecordFromProgress` такой лог в `moveLog` не пишет.
Флаг живёт в `PlayState`, а не в `DayProgress`, потому что `DayStore.persist()` пересобирает `DayProgress` из состояния стора, а `play` сохраняет как есть.
Старых «загрязнённых» записей практически нет: релиз 1 выкачен 2026-09-30, а синтетический лог мог появиться только при restore дня без `moveLog` (урезание бюджетом/413).

## г) Схема снапшота — без ломающей миграции

**Для Таймлапса 1.1 новых синхронизируемых полей не нужно** — достаточно существующего `DayRecord.moveLog` (+ `heat`/сводка для карточки). Поэтому:
`SNAPSHOT_SCHEMA_VERSION` остаётся 1, старые записи читаются как раньше, `hasTimelapse(rec)` просто отвечает «нет» на запись без `moveLog`.
Единственное новое поле — **локальное** `PlayState.logSynthetic` (опциональное; у старых записей IDB его нет = настоящий лог).

Предупреждения на будущее (PD-71 и далее):

- **Новые опциональные поля `DayRecord` молча стираются устаревшим клиентом**: `sanitizeDayRecord` собирает запись из известных полей и отбрасывает остальные; при
  равном `schemaVersion` старый клиент (PWA с закэшированным билдом, второе устройство) пересоберёт снапшот без них. Для одного владельца риск мал;
  для критичных полей — поднять `SNAPSHOT_SCHEMA_VERSION` до 2 (старый клиент уйдёт в `blocked: newer_schema`, а не затрёт данные) с миграцией `1 → 2` = тождественной.
- **Новый `MoveKind`/поле хода** — формат лога имеет префикс `1:`; старый `decodeMoveLog` на неизвестный вид возвращает `null`, а `sanitizeDayRecord` тогда молча
  выбрасывает `moveLog` всей записи. Решение — новый префикс `2:` и чтение обоих в новом клиенте (старые тогда «не видят» лог, но не портят остальное).
- Максимум экономии вместе с E: хранить в записи, есть ли в логе заметки — не нужно, определяется по содержимому.

## Что сделано в коде

**engine** (`packages/engine/src/timelapse.ts`, экспорт из `index.ts`, README, `timelapse.test.ts`, 34 теста):

- `timelapseFrames(log, { mission, solution? }, opts?) → { frames, durationMs, sourceDurationMs }`. Кадр: `{ t, move, cell, kind, values[81], notes?[81], wrong[] }`;
  первый кадр — пустое поле (подсказки есть), дальше по кадру на каждый ход, изменивший видимое состояние (no-op: `undo` без стека, `erase` пустой клетки, ход в подсказке,
  заметка в клетке с цифрой — кадров не дают, но их время остаётся в шкале). `opts`: `maxGapMs` (по умолчанию 3000; `Infinity` — не сжимать),
  `durationMs` (последний ход ровно в цель; перекрывает `speed`), `speed` (по умолчанию 1), `notes` (по умолчанию нет).
  Время: паузы → `min(gap, maxGapMs)` (включая «старт → первый ход»), затем масштаб; убывающий/нечисловой `t` читается как «не раньше предыдущего»; если сжатая длительность 0,
  а `durationMs` задана — кадры равномерно по индексу хода. Детерминирована, лога не меняет, результат — обычный JSON.
- `timelapseFingerprint(log, puzzle, { maxGapMs? }) → { cells[81], placed }`: на клетку игрока, верно заполненную к концу, `{ order, t, attempts }`
  (`order` — порядок финальной постановки 0…placed−1, `t` — 0…1 в **сжатом** времени, `attempts` — сколько раз ставили цифру); подсказки/неверные/пустые — `null`; цифр решения нет.
  Структура данных для PNG, рендера нет.

**web** (минимально; UI нет): `src/play/timelapse.ts` — `hasTimelapse(progress)`, `recordHasTimelapse(record)` (цельный лог: воспроизводится в решённую сетку,
не синтетический), `timelapseOf(progress, opts?)`; `PlayState.logSynthetic` и его проставление/учёт в `sync/schema.ts`; тесты `play/timelapse.test.ts`.

## Чернильный режим и повреждённые логи (PD-77)

- **Клякса (`Move.blot`, PD-71)**: `timelapseFrames` воспроизводит пару `place(неверная, blot) → place(верная, blot)` (один и тот же `t`) как два кадра подряд:
  в первом клетка в `wrong`, во втором уже верна; оба кадра несут `blot: true`, остальные — без поля. Шкала времени монотонна (равные `t` допустимы), финальный кадр
  ink-партии = решённая сетка. Кодек `2:` (лог с кляксой) читается тем же путём: `decodeMoveLog` → `hasTimelapse` → `timelapseOf`.
- **Отпечаток**: клетка, где была клякса, получает `blot: true` (только у таких); авто-замена — не попытка игрока (`attempts` считает кляксу, но не замену);
  `order`/`t` — момент замены. Цифр решения в данных по-прежнему нет.
- **Повреждённый лог**: `hasTimelapse`/`timelapseOf` (и `recordHasTimelapse`) на ходе с клеткой вне 0..80, `null` в логе или не-массиве возвращают `false`/`null`,
  а не бросают (движок `timelapseFrames` по-прежнему бросает `RangeError` — контракт). Ход `place`/`note_*` с цифрой не из 1..9 (например, `"x"` — раньше ставил бит 0
  в маске заметок) движок игнорирует как no-op.
- Формат снапшота не менялся: `SNAPSHOT_SCHEMA_VERSION = 1`, префиксы лога `1:` (обычный) / `2:` (есть `blot`).

## Открытые вопросы владельцу/PM

1. Оставляем бюджет `moveLog` 600 КиБ (вариант A)? Рекомендация — да; E/B — по факту 413 у реальных данных.
2. Нужны ли заметки в таймлапсе (UI-решение)? Данные есть (`opts.notes`), по умолчанию выключены.
3. Нужен ли «скорость/длительность» в UI таймлапса: `durationMs` (фиксированный ролик, напр. 15–30 с) vs `speed` (×1/×2/×4) — данные поддерживают оба.
